# The patch flow

A **patch** is a small change whose **solution is already fixed**: no spec, plan, tasks or walkthrough, only one `patch.md`. You arrive with the lane decided (`sdd-propose`, [Is it really a patch?](../../sdd-propose/references/patch-lane.md)). The lane's name isn't the git-flow branch type: a patch can leave as `feature/*` or `hotfix/*`, as the project's git-flow says.

One todo per step. Resuming, start at the first step whose output `patch.md` or the branch lacks, never with a second `patch.md`.

1. **Root cause, MANDATORY in a failure** (the intent, in a visual adjustment; the fixed solution, in a closed request) — `sdd-debugging` BEFORE proposing the fix. Never patch the symptom, and never implement the report's hypothesis without confirming it with evidence in the code. If the investigation shows the cause needs interpreting requirements, or the fix leaves something the user sees unfixed → STOP: it was a feature, move up through step 4 of `sdd-propose`, unless it's settled by choosing between options already written (step 3).

   If the investigation **doesn't reproduce the failure** on the current base → STOP too, without opening the patch: no branch, folder, `patch.md`, fix or reserved id. If the request comes from a roadmap row, leave it re-measured: the cells the result contradicts are rewritten with the new date and evidence, because adding the measurement and leaving the old text isn't enough. Tell the user. If it reproduces a **different** failure from the one the ticket or row predicts, that isn't this case: the patch goes on with the measured failure.

   **Visual adjustment variant** (the tree said «presentation only»): instead of the root cause, the **intent in one sentence** taken from the request («Guardar and Cancelar move from the header to a right column in `pedido-detalle` and `albaran-detalle`»), without `sdd-debugging`: there's no failure to reproduce, and the verification is step 4's screenshot. If writing the sentence makes you decide what moves or where, that's interpreting requirements: it's a feature. If a predicate condition falls while making the change —it needs an `@if`, a text or a line of TypeScript nobody fixed—, stop and move up through step 4 of `sdd-propose`, telling the user.

   **Closed request variant** (the ticket or the dev-lead fix the solution): instead of the root cause, the **fixed solution** —its literal sentence, with its author—, without `sdd-debugging`. Instead of reproducing a failure, check that what the request takes as existing exists (the destination, the element, the route): if not, STOP as with a failure that doesn't reproduce. The test of the requested behavior goes RED before the change, if the project has tests.
2. **Folder** — `.docs/sdd/specs/<yyyyMMdd-HHmmss>-patch-<id>-<slug>/` (UTC timestamp: `Get-Date -AsUTC -Format 'yyyyMMdd-HHmmss'`; `<id>` by the mode of `.docs/sdd/sdd-kit.json` (`ids.mode`; no field ⇒ `tracker`): in `tracker`, the ticket, and `0000` without one; in `sequence`, the id reserved in the roadmap row, or the one `sdd id next --reserve` reserves if it has no row (without `--reserve` it only proposes; another worktree can repeat it). With or without a row, before creating the folder run `sdd id claim --project-root "<root>"`: it checks the id against the remote integration, and if it prints `la <id> pasa a <nuevo>`, it already renamed the branch and the folder carries the new one; repeat that line to the user — it shares a sequence with features and an id is never reused between lanes (detail in [nombrado.md](../../sdd-propose/references/nombrado.md))). Artifacts live ONLY there: `.docs/sdd/patches/` or any other place doesn't exist, however tidy it looks. If you're on a `feature/<slug>` branch without an id (`feature/fix-sala`) and without commits of its own against the integration branch, rename it with `git branch -m feature/<id>-<slug>` before the first commit and say so; never rename the integration or stable branch: without this rule, 2 of 2 subjects committed on `feature/fix-sala` (`tests/sdd-roadmap-red.md`, p8b).
3. **`patch.md`** — traced from `patch-template.md` of `sdd-templates`: symptom (what was reported, literal; if the investigation measured another, also the measured one and how it differs), root cause (what YOU found, with the evidence; in a visual adjustment, the intent; in a closed request, the fixed solution), fix, verification, time. `solution:` says who fixed the solution (`causa raíz`, `ticket` or `dev-lead`), and the `Decisiones` list of §3 carries the author on each line: `ticket`, `dev-lead` or `sin el dev-lead`. A decision about what the user sees or can do with author `sin el dev-lead` takes the patch out of the lane: stop, as in step 4, and move up to feature through `sdd-propose`, or, if the ticket or the row already write the options, ask it closed to the dev-lead before going on. «It doesn't change what the user can do» doesn't hold if it changes what they see: a position, a text or an order you choose counts too. And your reading of what the dev-lead said is yours: author `sin el dev-lead`. If `.docs/sdd/estimation.md` exists, §5 carries from the start, before the fix, `- Estimación:` with the one `sdd-propose` brings —that of the lane question— or, with no question and none reaching you, the one you estimate before the fix, and `- Inicio:` with the UTC opening time. It holds even if the project's `estimation.md`, traced from an older template, says patches only record real time: that line is out of date; written at closing, with the real time in front of you, it contaminates the calibration (`tests/sdd-propose-0160-red.md`, a2).
4. **Minimal fix** — no opportunistic refactor, even with the debt one line away. Its test follows `sdd-tdd`: load it with `Skill`. Check the project's build passes. Before the commit, count the diff without tests or documentation (`git diff --numstat <merge-base>`): with more than 10 files or more than 300 lines, stop and ask the dev-lead whether it stays a patch or becomes a feature, with both counts. In a removal, search each removed symbol (handler, key, text) and leave in §4 that it has no other uses; one that still has uses isn't deleted.

   In a visual adjustment, the verification is **one screenshot per touched screen in a real browser before the change and another after** —the Playwright MCP or a script with the `playwright` package—, without tests: a unit test doesn't see the layout. With them apply [frontend-verification.md](frontend-verification.md): the `§Frontend` detector of `tech-stack.md` in its two viewports, and don't ask for validation with a finding open and unjustified; with `Detector: ninguno` or no `§Frontend`, §4 carries the warning «composición no medida: `tech-stack.md` no declara detector en §Frontend». In the RED, 0 of 2 subjects took the before screenshot or gave the warning (`tests/frontend-verification-red.md`, n1). The screenshot is kept **outside git** (the session's scratchpad), never in the patch's folder or the repo, and its path goes in §4 of `patch.md`: `sdd-archive` shows it to the user when asking for validation. In the RED, 1 of 2 subjects committed the screenshots in the patch's folder (`tests/visual-patch-red.md`, f1). If you start the application to look at it, stop it by its PID or its port, never by the executable's name. In a visual adjustment that isn't a removal, if the change needs an `@if`, a text or a line of code nobody fixed, stop: delete the patch's folder and its `patch.md` uncommitted, tell the user and move up through step 4 of `sdd-propose` with the half-done change as a starting point. The feature reserves its own id and the branch becomes `feature/<new id>-<slug>`: the patch's reserved id is consumed, because an id doesn't repeat between lanes.
5. **Verification** — before you say it's fixed, apply [The Gate Function](../../sdd-verify/SKILL.md#the-gate-function) of `sdd-verify`: run the fix's test, read its output, and §4 of `patch.md` carries the command and what it printed. A patch has **no final review** and no axes: before the fix commit, dispatch one reviewer (`subagent_type: sdd-kit:effort-medium`, `model: sonnet`) with `patch.md` and the diff, to check the root cause, the fix and its test, and answer each finding in §4: fixed, or rejected with its reason (dev-lead, 2026-11-04: «lite y patch minimo tendriamos que levantar uno en sonnet»).
6. **Fix commit** — one commit with the code, the tests and `patch.md`, with the project's convention and naming the ticket. The type follows the patch's class: `fix` only for a failure; the rest takes what the convention gives a change (`feat`, `style`…); intermediate commits are squashed ([commit-milestones.md](commit-milestones.md)). The debt row the patch settles is closed by `sdd-archive`; the fix commit doesn't touch it.
7. **Close** — invoke `sdd-archive` with `Skill`.

## Red flags — STOP

- You're implementing the reporter's hypothesis without confirming it in the code.
- You're about to create the document outside `.docs/sdd/specs/` or in a folder without the `patch-` prefix.
- You're about to decide something the user sees or can do that neither the ticket nor the dev-lead fixed → it was a feature.
- `patch.md` without `solution:`, without a root cause with evidence (or the intent or the fixed solution), or with the time blank.
- You're about to commit a screenshot, or close a visual adjustment without the paths of its before and after screenshots in §4, or without the detector's output (or its warning).
- You're about to open a branch or folder for a patch whose failure you haven't reproduced (except a visual adjustment, which has no failure, or a closed request, which checks what it takes as existing).
- You're about to dispatch a final review or an axis for a patch: it has step 5's verification and its one reviewer.

| Rationalization | Reality |
| --- | --- |
| "It's a one-line fix, no document needed" | One line without a trace is a regression waiting to repeat. `patch.md` costs 2 minutes. |
| "I don't want to open a whole task" | Right: a patch isn't a whole task. But a patch isn't no process: root cause + `patch.md` + close. |
| "It doesn't reproduce, but I'll leave the patch as coverage and a paper trail" | A patch without a failure consumes an id, a branch and a folder for nothing: 2/2 subjects of the RED did it (`tests/fewer-stops-red.md`, s5). Stop, and the row stays re-measured. |
