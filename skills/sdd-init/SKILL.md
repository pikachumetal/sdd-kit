# sdd-init

## Overview

Leave a project ready for the SDD flow: its anchor documents, a short `CLAUDE.md` with pointers, and the kit's configuration. Write everything the user reads in the language of their message. The content comes from an **interview with the user** and, when there is code, from **the code as it is today, not the ideal** — never from your guesses. Minimal documentation today; it grows with each task, so development doesn't stop.

**Never run Claude Code's `/init`**: it writes the monolithic `CLAUDE.md` this skill replaces.

Each document is written **only after the user approves it**, and its approval is recorded with `node "${CLAUDE_PLUGIN_ROOT}/cli/bin/sdd.js" init --root "<root>" --approved <path>`. Every `sdd <verb>` of this skill runs that way.

## ⛔ Gate: no interview, no documents

Invoking this skill starts the interview, not the generation. If the user is not there to answer, the init **waits at the first question or the first document**, in both modes: nothing is written. Turning questions into «documented assumptions» is not an interview: it is inventing a project.

## Entry predicates — in this order, the first that holds

1. **Template**: a `<!-- sdd-template: pending -->` in `.docs/sdd/` or in `PRODUCT.md`/`ROADMAP.md` → init over a template, **without code** whatever code it brings (a login and little more): complete only what is marked, in the shape its documents come in (2.x: `mission.md`, `tech-stack.md`…; 3.0.0: `PRODUCT.md`, `steering/`). Don't ask what the template already fixes (stack, commands, branches, worktrees) and don't touch its complete documents. The marker's position and count are the template's.
2. **Init in progress**: `.docs/sdd/sdd-kit.json` has the key `init` → read `init.approved` and `init.config`. Say which documents are approved, don't present them again, don't ask again what `init.config` holds, and go on with the first document missing in the generation order; with all approved, go on with git. Only `init.approved` counts as approved, never what is on disk.
3. **Initialized**: `.docs/sdd/sdd-kit.json` without `init` → invoke [`sdd-upgrade`](../sdd-upgrade/SKILL.md) with `Skill`; don't migrate from here, and don't re-initialize.
4. **2.x documents without marker**: `.docs/sdd/mission.md` or `.docs/sdd/constitution.md` without `sdd-kit.json` → ask, migration recommended: a project older than v0.2.0 (invoke `sdd-upgrade`, which applies them all) or a 2.x init that was cut (a new init, with those documents as harvest material).
5. **Otherwise** → new init. A previous `PRODUCT.md`, `CLAUDE.md`, `CHANGELOG.md` or `ROADMAP.md` doesn't decide anything: it is harvest material.

## Mode

- **With code**: the root has `package.json`, `*.csproj`, `*.sln`, `pom.xml`, `build.gradle*`, `pyproject.toml`, `go.mod`, `Cargo.toml`, `composer.json` or `Gemfile`, or, outside `node_modules/`, `.git/` and `.docs/`, a `.ts`, `.js`, `.cs`, `.java`, `.py`, `.go`, `.rs`, `.php`, `.rb`, `.kt` or `.swift` file.
- **Without code**: anything else, and every template.

Before the first question, say the mode in one line: «Modo: sin código» or «Modo: con código — si es un template recién instanciado, dímelo y sigo sin código». If the user corrects it, go on with theirs.

## Flow (one todo per step)

1. **Inventory** *(with code)* — the real stack (manifests), modules, observed patterns, debt signals (duplication, TODOs, contradicting docs, blocked dependencies), commands and test scripts (scripts, CI), environment scripts per worktree (`env:*`, `worktree:*`), branches and the remote's default one. In medium or large codebases, delegate it to subagents on cheap models (sonnet/haiku). What can't be verified is marked as such.
2. **Harvest** — every file that already exists in the root (`CLAUDE.md`, `PRODUCT.md`, `CHANGELOG.md`, `ROADMAP.md`, one generated by `/init` included): each claim verified in the code goes to the document it belongs to; an unverified one goes to the discrepancies list for the user. Nothing is lost in silence, and none of them is overwritten without its gate: its new version is presented with the diff against the old one.
3. **Interview** — ask with the `sdd-grilling` skill (invoke it with `Skill`): one question, or one document to approve, per turn. «No sé» leaves the entry pending; «no aplica» closes it. What exists (code, a harvested document) is presented as a proposal to confirm, and what the user's instructions (global or project `CLAUDE.md`) already fix is not asked: it is referenced. *With code*: the column «With code» says what you propose instead of asking.

   | Topic | With code | Goes to |
   | --- | --- | --- |
   | Problem it solves; users and roles; modules; what is out of scope; domain terms to fix | proposed from the code; out of scope and terms, asked | `PRODUCT.md` (modules → `ROADMAP.md`) |
   | The five product rules, by name: where data lives (file, table, memory, client storage) · naming language (API, keys, messages) · limits (sizes, depths, number of results) · warnings (what the user is warned of, and when) · conflict rule (which wins when two ways give the same data) | deduced from the code as proposal; what can't be deduced, pending | constitution, «Reglas de producto» |
   | Stack: if undecided, options with trade-offs and your recommendation; the user decides, and it can stay open with its options | read from the manifests | `architecture.md`; open → a Next row |
   | What is non-negotiable (data, migrations, security; commits, only if the user's instructions don't fix them) | observed conventions as proposal | constitution |
   | How it is tested: each suite with its command and duration, where it leaves its temporary files, the affected-tests command, the closing gate and the merge gate, how the agent gets into the app, whether tests use the production engine; with E2E, the template's E2E fields | from the scripts and CI; durations and the E2E budget `pendiente` unless the user says them. An `e2e` script without tests is still a suite, without the E2E fields. With E2E tests: the flows of the E2E files found, as candidates, and the user says which are core; retries and timeouts read from the runner's config with their real value, and a raised timeout with no written reason is written as such («60 s por test, sin motivo escrito»). «Temporales»: where each suite writes them today, from its config or else the runner's default (Playwright without `outputDir`: `test-results/`), and the proposal to move them to `.temp/` (`outputDir: '.temp/playwright'`); if neither says it, `no declarado`, no proposal; after a «no», only the place; never edit the suite's config nor add roadmap rows | `operations.md`, `## Testing` |
   | Changelog? | asked | `CHANGELOG.md` |
   | Ticket tracker? | asked | `CLAUDE.md` |
   | Branch convention: git-flow recommended (`main` stable, `develop` integration, `feature/<id>` from `develop`) | the convention the repo shows, recommended; git-flow as alternative | constitution and git step |
   | Worktrees? Then, only if yes: does a worktree's environment need more than installing dependencies (DB, ports, services, data)? | environment scripts found → proposed | `CLAUDE.md`; `operations.md`, `## Entornos` |
   | The kit's keys: invoke the [`sdd-config`](../sdd-config/SKILL.md) skill with the integration branch of the branch question. It asks, one per turn with its recommendation, how work is numbered (`ids.mode`), control profile, merge and push policy (only with an integration branch other than the stable one), brakes, execution method, who validates (`validation.mode`), what happens to final-review Minors (`review.minors`) and the price table (`pricing`). Record its answers at once with `sdd init --config '<json>'`, only what was answered: «no sé» writes no key | asked | `sdd-kit.json` |
   | Does it replicate another project's patterns? Which one? («no» leaves «no aplica») | asked | constitution, «Convenciones» |
   | Only with an interface: what verifies what is seen — detector, E2E runner and how the agent gets in (the entry URL if there is login); recommended, impeccable and Playwright. «Sin detector» stays as `Detector: ninguno` | UI framework found → asked | `operations.md`, `## Frontend` |

   Ask the five product rules by name: without them the agent decides them at random in each feature. Without code, «¿Cómo se prueba?» goes with the recommendation that follows from the stack, and every field without an answer stays `no declarado`.
4. **Documents, one by one, each with its gate** — in this order: `PRODUCT.md` (root) → `.docs/sdd/steering/constitution.md` → `.docs/sdd/steering/operations.md` → `.docs/sdd/steering/architecture.md` → `ROADMAP.md` (root) → `.docs/sdd/steering/debt.md` *(with code: the inventory's debt and blocks, in «Por triar»)* → `.docs/sdd/steering/estimation.md` (empty calibration) → `CHANGELOG.md` (root, only if the interview says yes) → `CLAUDE.md`. For each: present the draft in the chat, wait for the «sí», write the file, record it with `sdd init --approved <path>`. Order and what each one carries: [references/generation.md](references/generation.md).
   - Each document is **traced** from its template of `sdd-templates` ([references/structure.md](references/structure.md)): the form is the template's, the content is the interview's or the confirmed code's. Never copy a document from the kit's `.docs/` or another project's, and never create a `templates/` folder. Versions live in the manifests, not in the documents.
   - *With code*: the constitution proposes the observed conventions **as proposals** the user confirms or corrects, article by article, plus the brownfield golden rules of [references/generation.md](references/generation.md).
   - **Contributed functional brief** (a document, an email, pasted text): verbatim in `.docs/sdd/sources/`, with its original name or as `<yyyyMMdd>-functional-brief.md` if pasted, never edited. `PRODUCT.md` links it; each `ROADMAP.md` row from it cites its section (`sources/<file> §<n>`). No capability is born from it.
   - **`CLAUDE.md` goes through its gate like the others**: pointers to the documents plus 3-5 critical rules, nothing that already lives in an anchor document; the ticket tracker and worktrees from the interview. A previous `CLAUDE.md` follows step 2 even when resuming: an unverified claim goes to discrepancies, never into the new file as a rule.
   - `capabilities/`, `changes/` and `decisions/` are not created: git doesn't version empty folders, and none is created empty or with `.gitkeep`. They are born with their first file.
5. **Estimation log** — `sdd estimation log --root "<root>"`, which leaves `.docs/sdd/steering/estimation-log.md` with its header and no rows. Never by hand; the script stays in the kit.
6. **Git** — `git init` if there is no repo. If its branches or remote don't follow the agreed convention, present the full plan — renames, new branches, the remote's default branch, deletions — and wait for the «sí». The user runs what touches the remote (push, default branch, deleting branches), with your commands.
7. **Finish** — `sdd init --root "<root>" --finish`, with `--ignore <path>` for the session path `## Frontend` declares. It writes, in this order and without asking: `.claude/settings.json` (memory off, `extraKnownMarketplaces.sdd-kit` and `extraKnownMarketplaces.superpowers-marketplace` with `autoUpdate`, both plugins in `enabledPlugins`; it merges leaf by leaf and leaves what has another value, saying so), `.gitignore` and `.docs/sdd/sdd-kit.json` with the kit's `version` (a template keeps its own), `channel: plugin`, the date and the `init.config` answers; then it drops `init`. If it prints `autoMemoryEnabled: se deja true; pregunta al usuario si lo cambia`, ask; with a «sí», run `--finish` again with `--memory-off`; with a «no», the closing summary notes it. If `claude plugin marketplace list` doesn't show `superpowers-marketplace`, run `claude plugin marketplace add obra/superpowers-marketplace`.
8. **Closing summary** — what was created; discrepancies and pending questions; that personal preferences (profile, method, environment at validation) are set with `sdd-config`; after a 2.x template, that the migration brings it up to date; next steps: estimation as `capabilities/` matures, and level 2/3 skills for the tribal knowledge (build, backend and frontend patterns), which this skill doesn't create.
   **Initial capability dump, only if the user asks for it** (never offer it), in both modes: read the whole code — if you can't read it all in this session, say so and don't dump; before writing any file, propose the partition (each capability with its slug in English kebab-case and a domain noun, rule 1 of `capability-template.md`; a code module's name is not a capability name) and wait for the «sí»; write each one tracing `capability-template.md`, with what the code does today, and present it with the same gate as the anchor documents.

## Red flags — STOP

- You're writing `PRODUCT.md` or the constitution and the user hasn't answered the interview.
- You're about to write a document, `CLAUDE.md` included, without its «sí» in this session or in `init.approved`.
- You're treating a file on disk as approved because it exists.
- You decided the MVP scope, a role or the stack yourself «as a reasonable proposal».
- You're copying claims from the old `CLAUDE.md` into the docs without verifying them in the code.
- Everything is ending up inside `CLAUDE.md` (a monolith) instead of in the documents.
- The constitution declares conventions the user hasn't confirmed, without marking them as proposals.
- You were about to launch `/init`.
- The debt you found stays in loose notes instead of `debt.md`.
- You're creating `docs/` or `docs/superpowers/` instead of `.docs/sdd/`.
- The estimation log is born with rows, or written by hand.
- You're dumping capabilities the user didn't ask for, or writing one before the partition is approved.
- You're presenting a template's code as the state of the project.

| Rationalization | Reality |
| --- | --- |
| «The user isn't answering: I'll turn the questions into documented assumptions» | That is inventing a project. The interview WAITS: your last message is its first question. |
| «I'll mark everything as a pending draft and move on» | Hundreds of lines of guesses anchor future conversations to YOUR decisions. A short approved document beats eight invented drafts. |
| «The file is there, so it was approved» | A file on disk can come from before the init, from impeccable or from a cut session. Only `init.approved` says approved. |
| «The CLAUDE.md already says it, I'll reuse it» | Inherited CLAUDE.md files lie (stale versions, phantom folders). Each claim is verified or becomes a discrepancy. |
| «I'll rewrite the CLAUDE.md better and done» | An honest monolith is still a monolith: a huge context in every conversation. Layers plus pointers, through its gate. |
| «The repo is small, I don't need subagents» | Right: subagents are for medium or large codebases. The result's shape doesn't change. |
| «It has code, so it's brownfield» | A freshly instantiated template is greenfield: its code is a starting point, not the project's state. |
| «The kit says capabilities grow feature by feature: I refuse to dump them» | At the user's request the dump is the written exception of step 8. Refusing is the failure the RED showed (1/2): apply its conditions. |
| «The code is small: I'll dump the capabilities and show them at the end» | The partition is approved before writing any file. In the RED, a direct dump named the capabilities after the code's modules. |
