# sdd-config

## Overview

The kit's configuration lives in two files: `.docs/sdd/sdd-kit.json`, the project's, in git; and `.docs/sdd/sdd-kit.local.json`, each person's, outside git. This skill is the kit's only interview of keys: the user invokes it, and `sdd-init` and the migrations invoke it instead of carrying their own questions. What each file admits, the precedence and the warnings are in the contract: [control-profiles.md](../sdd-start-feature/references/control-profiles.md). Talk to the user in their language.

## Steps

1. **Read and show** — read `.docs/sdd/sdd-kit.json` and `.docs/sdd/sdd-kit.local.json` (even if listing the folder doesn't show it). Before the first question, show a table with every key of the catalog: its value and the file it comes from, or «falta» and the default that applies. Below, one warning per ignored key of the local file, with the contract's literal line. Invoked by an init or a migration, the table carries only what exists.
2. **Ask** — only what is missing, or what the user asks to change. **Ask with the `sdd-grilling` skill** (invoke it with `Skill`); the recommended option and its reason come from the catalog; «decide tú» writes it. A key with a value isn't asked again unless the user asks. Invoked by the user, first ask who `control.profile` or `execution` applies to: «¿para todo el equipo (`sdd-kit.json`) o solo para ti (`sdd-kit.local.json`)?». Recommend «solo para ti» if the project already has the key, and «para el equipo» if it's missing.
3. **Write** — each answer, in its file (the catalog's «File» column). If an init or a migration invokes you, you don't write: you return the answers and whoever invoked you writes them in `sdd-kit.json`, in its structure or marker step. So `sdd-kit.json` isn't born without `version` if the session is cut, and an init sets the project, not whoever runs it. «No sé» writes nothing and its default applies; what wasn't asked isn't written. That answer is the user's phrase: writing it isn't the self-granted shortcut. Before creating `.docs/sdd/sdd-kit.local.json`, check that `.gitignore` has that line and add it if missing, without duplicating it. The local file is never committed and carries nobody's name: the name comes from `git config user.name`. A `field` answer to question 7 removes the validation stop from the closings: its literal phrase and the date go in the body of the commit that carries `sdd-kit.json`; if you don't commit, give them to whoever does.
4. **Without a user** — write nothing. Return the pending questions to whoever invoked you, for their report or closing summary. The defaults apply.

## Catalog

| --- | --- | --- | --- | --- |
| 1 | How are features numbered: ids from the ticket tracker (`tracker`) or the project's own sequence (`sequence`)? | Recommended `tracker` if there is a ticket tracker: the id links the feature to its ticket. Without one, `sequence` | the answer: `ids.mode`; «no sé»: nothing, and `tracker` applies | `sdd-kit.json` |
| 2 | Which control profile do you work with: `pair`, `delegate` or `unattended`? | Recommended `delegate`: it stops at the spec, at deviations and at validation, and saves the plan gate; with fewer stops, 0.6.0 closed three tasks in a day | `control.profile` | the one the user says; in an init or a migration, `sdd-kit.json` |
| 3 | When a feature closes, do I merge into `<integration branch>` with `--no-ff` and leave deleting the worktree to a person? | Recommended yes: `--no-ff` leaves the feature in one commit that reverts at once, and deleting a worktree with uncommitted changes is irreversible | «sí»: the whole `merge` (`into`: the branch, `noFf: true`, `removeWorktree: false`); another combination said in full: that one; «no» or «no sé»: nothing, and the feature closing asks | `sdd-kit.json` |
| 4 | After merging into `<integration branch>`, do I push that branch to its remote without asking? | Recommended yes if the convention is `main` stable and `develop` for integration (git-flow): the integration branch is shared, and a merge without a push is seen by nobody else; the stable branch, the tags and any other push stay a person's. With another convention, no recommendation | «sí»: `merge.push: true`; «no»: `merge.push: false`; «no sé»: nothing, and the closing doesn't push | `sdd-kit.json` |
| 5 | Are the default brakes fine for you: up to 3 agents in parallel, and a warning after 8 minutes of silence between steps or after 20 in a long command? | Recommended yes: they are the kit's defaults; the agent cap is applied by [sdd-parallel-agents](../sdd-parallel-agents/SKILL.md) and the silence watch by [control-profiles.md](../sdd-start-feature/references/control-profiles.md#vigía-de-silencio) | «sí» or own numbers: `control.maxParallelAgents`, `control.silence.betweenStepsMinutes`, `control.silence.longCommandMinutes`; «no sé»: nothing, and the defaults apply | `sdd-kit.json` |
| 6 | How are plans executed: `auto` (each plan recommends its method), `native` (in the session; after a compaction with two or more pending tasks, the rest goes with subagents) or `subagent` (always with subagents)? | Recommended `auto`: the handoff of `plan-writing.md` of `sdd-propose` weighs each plan: Native is the cheapest; subagents, for long plans or a review per task | the answer: `execution`; «no sé»: nothing, and `auto` applies | the one the user says; in an init or a migration, `sdd-kit.json` |
| 7 | Who validates the work at closing: the dev-lead, trying it (`manual`), or real use, through the `sdd-feedback` tickets (`field`)? | Recommended `manual`: with `field` nobody stops to try it at closing, and a screen, a CLI or an API can be tried then. Recommended `field` only if the project has no screen or use the dev-lead can try at closing, like a skills kit only tested by use in other projects. Look in `mission.md` and `tech-stack.md`; in a greenfield init, in the product and stack answers | the answer: `validation.mode`; «no sé»: nothing, and `manual` applies | `sdd-kit.json` |
| 8 | When it's your turn to validate a feature, do you want me to start the environment before giving you the test script? | Recommended no, the default: the validation says how to start it. Yes, to find the application running | «sí»: `validation.startEnvironment: true`; «no»: `false`; «no sé»: nothing | `sdd-kit.local.json` |
| 9 | When the final review returns Minor findings, do they enter the fix pass (`fix`) or go to the ledger as deferred (`defer`)? | Recommended `defer`: a Minor doesn't change what the product's user gets, and each fix lengthens the fix pass. `fix` to close them in every feature | the answer: `review.minors`; «no sé»: nothing, and `defer` applies | `sdd-kit.json` |
| 10 | Do I write the price table, so the closing gives the session's cost? | Recommended yes. Before asking, read https://platform.claude.com/docs/en/about-claude/pricing and put the proposed table in the question: one row per current Opus, Sonnet and Haiku model, by API id (`claude-sonnet-5-5`), with its five prices. Can't read the page: say so, no recommendation, never made-up prices | «sí»: `pricing.usdPerMillionTokens.<model id>` with `input`, `cacheWrite5m`, `cacheWrite1h`, `cacheRead`, `output`; `pricing.source`: the page; `pricing.updated`: the date read; «no» or «no sé»: nothing, and the closing gives «sin precio». An update rereads the page and keeps rows it no longer lists | `sdd-kit.json` |

- **Who asks what**: an init or a migration do 1 to 7, 9 and 10, in that order, skipping those that already have a key. Question 8 is personal: only the user who invokes the skill gets it. With `pricing` written, the table shows its `updated` and its models.
- **Integration branch** of questions 3 and 4: the one of the branch convention (greenfield) or the one seen in the repo (brownfield); whoever invokes passes it. If integration goes straight to the stable branch, question 3 isn't asked and `merge` stays undeclared: the merge into the stable branch is always a person's decision.
- **Push** of question 4: only if question 3 left `merge` declared: without it, there is no merge to push.
- **Policy keys**: `ids`, `merge`, the brakes, `review.minors`, `pricing` and any other that isn't `control.profile`, `execution` or `validation.startEnvironment` always go to `sdd-kit.json`. Asked for one only for themselves, explain it belongs to the project and offer to change it for the team.
