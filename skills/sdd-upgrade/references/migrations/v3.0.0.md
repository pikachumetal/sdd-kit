# Migration to v3.0.0 — the documents to the structure of 3.0.0

Applies to any project with any of these 2.x documents in `.docs/sdd/`: `mission.md`, `tech-stack.md`, `environments.md`, `constitution.md`, `architecture.md`, `estimation.md`, `estimation-log.md`, `changelog.md` or `roadmap.md`. Since v3.0.0, what the person reads goes at the project's root (`PRODUCT.md`, `ROADMAP.md` and `CHANGELOG.md`) and what the agent reads, in `.docs/sdd/steering/` (`constitution.md`, `operations.md`, `architecture.md`, `debt.md`, `estimation.md` and `estimation-log.md`). The templates are those of `sdd-templates`: `PRODUCT-template.md`, `operations-template.md`, `now-next-later-template.md` and `debt-template.md`.

**What doesn't move**: `capabilities/`, `decisions/`, `specs/`, `releases/`, `kit-feedback/`, `sources/`, `sdd-kit.json`, `sdd-kit.local.json` and `client-changelog.md`. New changes are born in `changes/`; the folders of `specs/` stay and are still read.

**How each step with a table is applied** (steps 1, 2 and 3 carry a table and a gate each; step 4 runs only if step 1, 2 or 3 moved something; from 5 to 10, what each one says):

1. **Predicate.** If it doesn't hold, skip the step and say so.
2. **Starting point.** `git status --short` over the step's files has to come out empty; if not, stop and say so. Note `git rev-parse --short HEAD`: it's the sha of what was before.
3. **Destination table**, one row per block (a document, a section, a roadmap row) with its destination per the step's recipe. For each value the new form requires and the old one didn't have, the table says where it comes from. What is rewritten (a glossary, a condensed section) goes with the resulting text, and what is lost (a cell with no column in the destination) goes named.
4. **gate** — present the table and wait for the «sí». If the dev-lead changes a destination, you apply theirs. If they reject it or aren't there, the step stays **explicitly pending**: nothing moved, nothing staged, and the table in the report with «para reanudar: aprueba la tabla y vuelve a pedir la migración».
5. **Apply** without rewriting the text, except the links and what the approved table already shows rewritten. A document that lands in another folder (moved, or written from one that stays behind) rewrites its relative links for that folder: inline `](…)` and reference `[x]: …`, not those inside code, URLs or anchor-only ones; in `CHANGELOG.md`, only the part that comes from `.docs/sdd/changelog.md`. A move is a `git mv`, which keeps the history (`git log --follow <ruta nueva>`). A file that already exists in the destination (a `PRODUCT.md` from impeccable, a `CHANGELOG.md`) is merged section by section, as the table says: neither overwrites the other.

The steps go in this order.

1. **Moves.** If any of `.docs/sdd/changelog.md`, `constitution.md`, `architecture.md`, `estimation.md` or `estimation-log.md` exists. A single table:

   | What there is | Destination |
   | --- | --- |
   | `changelog.md` | `git mv .docs/sdd/changelog.md CHANGELOG.md` (at the root). With a `CHANGELOG.md` already at the root, the table proposes how they merge |
   | `constitution.md`, `architecture.md`, `estimation.md` | `git mv .docs/sdd/<doc> .docs/sdd/steering/<doc>` (create the folder first). Their content doesn't change, except the relative links that break when going down one level: `decisions/0001-…` becomes `../decisions/0001-…`, and `capabilities/…`, `../capabilities/…` |
   | `estimation-log.md`, with `estimation.md` | The table shows the diff between the current log and the one `sdd estimation log --root "<raíz>" --out <carpeta temporal>/estimation-log.md` generates, because the regenerated one overwrites the rows written by hand. After the «sí», `git mv` to `steering/` and `sdd estimation log --root "<raíz>"`, which regenerates it in its new place |
   | `estimation-log.md`, without `estimation.md` | Propose in the table what is done with it: to `steering/` without regenerating, or out |

2. **Product and operations.** If `.docs/sdd/mission.md`, `tech-stack.md` or `environments.md` exists.
   - **`mission.md` → `PRODUCT.md`** at the root, with the headings of `PRODUCT-template.md`:

     | 2.x section | Destination |
     | --- | --- |
     | «Por qué existe» | `## Product Purpose` |
     | «Usuarios y roles» | `## Users` |
     | «Qué es y qué no es» | `## Capabilities and Constraints` |
     | «Dominio» | `## Terminology`, each term as `**Término**: <definición>`, and `_Evitar_: <sinónimos>` only if the original names the synonym it avoids; the table shows the resulting text |
     | Another section | Propose its destination in the table |

   - **`tech-stack.md` and `environments.md` → `.docs/sdd/steering/operations.md`**, with the headings of `operations-template.md`:

     | 2.x section | Destination |
     | --- | --- |
     | «Comandos», «Testing», «Frontend» | The section of the same name, as is. `## Testing` gains the level of each suite, «Sin filtro», «Lint» and «CI de la base» of `operations-template.md`, proposed as in the init (`sdd-init`, row «How it is tested»): the level only if the config or the code of the suite says what it starts (a Playwright config is `E2E`, whether or not it already has tests), otherwise `pendiente`; «Lint» with a `lint` or `format` script, or what the pre-commit runs (`lint-staged`, a husky hook), even without a config file, and `ninguno` only without either of the two; «CI de la base» with the pipeline that exists and, with GitHub Actions, `gh run list --workflow <fichero> --branch <merge.into> -L 1 --json conclusion,headSha`, written as is without running it, also without a remote (another pipeline, `sin orden de lectura`; none, `ninguna`). The gate line isn't rewritten: with a moon gate with `--affected` and without `-g` or `--include-relations`, the table proposes adding `--include-relations`, and a suite whose command is the gate's isn't proposed separately. `## Testing` always gains the «Temporales» field of `operations-template.md`, with or without E2E, proposed as in the init; with E2E, `## Testing` gains the six E2E fields of `operations-template.md`, proposed the same way: «Flujos core», the ones the dev-lead chooses among those of `e2e/`, and the table offers the titles test (`sdd-tdd/references/writing-e2e.md`, rule 1): with the «sí», write it green, with «Títulos heredados»; «Retries» and «Timeouts», with the value of the runner's config, and a timeout raised without a reason, literal: «60 s por test, sin motivo escrito»; «Presupuesto E2E», `pendiente`; «Entorno de la suite», the script that starts what the suite needs (`env:up`, `docker compose up`) with the check that it responds, or `pendiente`; «Datos», `pendiente` if the dev-lead doesn't say it |
     | `environments.md` | `## Entornos`, condensed to the marker, the three entries and the runner; the table shows the resulting text. Without `environments.md`, `## Entornos` isn't written, and you say so |
     | «Tecnologías» | What the manifests already say (`package.json`, `*.csproj`, `go.mod`…) leaves; what isn't in any of them (a service, a runtime pinned by hand) goes to `steering/architecture.md` |
     | «Decisiones abiertas» | They go to the table of step 3, which takes them to Later |
     | Another section (learnings, notes) | Propose its destination: `operations.md`, `architecture.md`, `constitution.md` or out |

   After the «sí», write `PRODUCT.md` and `steering/operations.md`, and then `git rm` of `mission.md`, `tech-stack.md` and `environments.md`: none of them is moved with `git mv`, because they change form. The report and the commit body carry `git show <sha>:.docs/sdd/mission.md`, and the same for the other two. If step 3 stays pending, the report names next to it each «Decisión abierta», with `git show <sha>:.docs/sdd/tech-stack.md`: until it's approved, it's its only place.

3. **Roadmap and debt → `ROADMAP.md` and `.docs/sdd/steering/debt.md`.** If `.docs/sdd/roadmap.md` exists. A single table and a single gate for both, because both come from the same file: a half-done roadmap isn't left.

   **Published**: the last closed release is the newest version of `changelog.md`. A row was published if the commit that added its closing artifact (`walkthrough.md` or `patch.md`) is in that version's git tag (`git merge-base --is-ancestor <commit> v<versión>`): not the commit that added the row, its date or «Releases cerradas», because a hotfix leaves from `main`. A row without an artifact goes to the table; without tags, the table asks once for all rows. «After the last closed release» below means not published.

   **`ROADMAP.md`**, at the root, with the form of `now-next-later-template.md` and the equivalences of `sdd-roadmap`:

   | What there is | Destination |
   | --- | --- |
   | `## Release <N>`, or «Próximo» rows that open with `**Release <N>**` (N in SemVer, with or without `Patch: ` before it, any punctuation after) | Its rows to Now, with the title `## Now — <versión> · en preparación`; `Perfil de control: <perfil>` only if the release said it. Two different N, or an N that isn't SemVer, go to the table with the question. Without a release, neither a version title nor a profile line |
   | «Próximo» | With a release in preparation: a `✅` or `🧪` row not published goes to Now, a published one or one the row marks absorbed or discarded leaves, named in the table, and the rest go to Next. Without one, to Now |
   | «Backlog» | To Later, keeping the sequence id it already has, otherwise with an id from the reservation (below), its «Origen» at the end of the one-liner and «Estado» `⏳`; a row with a `**[… saldada …]**` prefix leaves, and one with `parcial` goes with the «Ítem» rewritten to what remains. «Tamaño» and «Tras», `—` |
   | «Decisiones abiertas» of step 2 | To Later, after the «Backlog», with an id from the same reservation, «Estado» `⏳` |
   | «Patches», after the last closed release | To Now with `✅`: title = its «Descripción», the date in the one-liner, `**Carril:** patch` and `**Requisitos:**` toward its `patch.md` if the description links it. One whose id is already in «Próximo» joins that row |
   | «Patches», earlier | They leave: they're in `CHANGELOG.md` |
   | «Releases cerradas» | It leaves: it lives in `CHANGELOG.md` and in `releases/`. Its `validaciones pendientes:` don't go to Now (a feature of a closed release has no row in an open section): the table and the report name each one, which stays in its walkthrough or its `patch.md` |
   | A row without an id (a milestone) | Ask in the table: Later, or a new id with `sdd id next --reserve`; with a state Later doesn't admit (`🔄`), also which state it takes |

   **Ids of Later**: in `sequence`, a single reservation `sdd id next --reserve --count N` for the N rows of the «Backlog» and of the «Decisiones abiertas» without a sequence id, in the order they appear; in `tracker`, `0000`. No row carries `B<n>`.

   Each row of Now and Next, with the template's form:

   - **«Tarea»**: the title and the one-liner come from the «Ítem» (or from «Feature» in a release); the folded brief, from these sources: `**Carril:**` from the «Patch:» prefix (without it, `feature`); `**Requisitos:**` from `proposal: <id>`; `**Toca:**` from «Ficheros que toca»; `**Salda:**` from the debt row that points to it with `**Actuar**`; what has no source, `—`.
   - **«Externo»**: the Jira, Azure DevOps or GitHub id the «Ítem» names; without an id, `—`.
   - **«Tras»**: the ids of «tras NNNN». An id that doesn't stay in `ROADMAP.md` and isn't in `CHANGELOG.md` becomes `—`, and the table warns about it.
   - **«Estado»**: `⏳`, `🔄`, `✅`, `🧪` and `⏸️` pass the same; another one (`❌ descartado`) goes to the table with the question of its destination.
   - **«Tamaño»**: it isn't deduced, also not in the `✅` rows. The table leaves it as «lo decide el dev-lead», and the gate doesn't close without it (`S`, `M` or `L`).

   **`steering/debt.md`**, with the form of `debt-template.md`, by the «Destino» of each row of «Deuda técnica». Any of its forms counts as `**Actuar**`: `**Actuar**: <id>`, `**Actuar** → <id>`, `**Actuar → <id>**` or `**Actuar** en la <id>`. The rows, in this order of precedence, the first that matches:

   | 2.x row | Section | Cells |
   | --- | --- | --- |
   | With a `**[… saldada …]**` prefix, after the last closed release | «Lista» | The «Ítem» with its prefix intact; «Evidencia»: the prefix's link; «Destino»: the prefix's id |
   | With a `**[… saldada …]**` prefix, earlier | It leaves | — |
   | With a `parcial` prefix, earlier or later than the last closed release | The section of its «Destino», by the rows below | The «Ítem» rewritten to what remains |
   | `**Actuar**` to an id or `sin fila`, with evidence in the «Ítem» (a link, a ticket, a figure) | «Lista» | «Destino»: the id or `sin fila`; «Evidencia»: the one of the «Ítem» |
   | `**Actuar**` without evidence in the «Ítem» | «Por triar» | — |
   | `**Esperar 2.º ticket**` | «En espera» | «Falta»: what it says after the destination, without the `· causa:` marks or the word `falta` |
   | `**Descartada**` | It leaves | — |
   | Any other destination (`versión siguiente`, a sentence) | «Por triar» | — |

   In every section:

   - **«Origen»**: one link per case, to the ticket or the walkthrough the «Ítem» cites; if a case cites both, the ticket, and the walkthrough goes to «Evidencia»; with neither, `roadmap 2.x`.
   - **«Causa» and «Arreglo»** («En espera», the cause; «Lista», both; a row with a `**[… saldada …]**` prefix doesn't carry them): they come from `· causa:` and `· arreglo:` of its «Destino». Without them, the table shows the value it proposes reading the «Ítem», with the definitions of `debt-template.md`: `defecto del producto (propuesta)`, not «te lo propongo luego», and the fix, one of the template's (`—` with that cause); the dev-lead approves it in that gate and the cell goes without the mark. A row whose cause they reject goes to «Por triar». Without knowing the cause of one of «En espera», `sin determinar`.
   - **«Remedio temporal»** («Lista»): it comes from `· remedio:`; without it, `—`, and with two or more links in «Origen» the table asks the dev-lead.
   - **Relative links** (in «Origen», «Evidencia» or the «Ítem»): they gain `../`, because `debt.md` is one level below `roadmap.md`: `field-reports/x.md` becomes `../field-reports/x.md`.
   - **«Fecha»** («Por triar» and «En espera»): the one of the commit that added the row, `git log -S'<primeras palabras del ítem, sin marcas ni backticks>' --format=%as --reverse -- .docs/sdd/roadmap.md`, the first line. The table says where each one comes from. Without a result, ask the dev-lead for it: never today's.
   - **«Impacto»** passes as is in «En espera» and «Lista». In «Por triar» there's no column: the table names it as what is lost, and the dev-lead decides whether it goes to the «Ítem».

   After the «sí», write `ROADMAP.md` and `steering/debt.md`, and only then `git rm .docs/sdd/roadmap.md`. The report and the commit body carry `git show <sha>:.docs/sdd/roadmap.md`.

4. **Links.** If step 1, 2 or 3 moved something. Look for the Markdown links that point to an old path of what moved, in the whole repo except the history, and the old paths written between backticks in `CLAUDE.md`, `AGENTS.md` and `README.md`:

   ```bash
   git grep --untracked -nE '\]\(([^)]*/)?(mission|tech-stack|environments|roadmap|changelog|constitution|architecture|estimation|estimation-log)\.md[)#]' -- . ':!.docs/sdd/specs' ':!.docs/sdd/changes' ':!.docs/sdd/releases' ':!.docs/sdd/kit-feedback' ':!.docs/sdd/field-reports'
   git grep --untracked -nE '`\.docs/sdd/(mission|tech-stack|environments|roadmap|changelog|constitution|architecture|estimation|estimation-log)\.md`' -- CLAUDE.md AGENTS.md README.md
   ```

   Discard from the output the links that already point to `steering/` and those from a file of `steering/` to a sibling, without a folder (`](architecture.md)` inside `steering/constitution.md`): they're still right. Fix the others to their new path, computed from the folder of the file that links, only if its document moved in this step or an earlier one:

   | Old path | New path |
   | --- | --- |
   | `.docs/sdd/mission.md` | `PRODUCT.md` |
   | `.docs/sdd/tech-stack.md`, `.docs/sdd/environments.md` | `.docs/sdd/steering/operations.md` |
   | `.docs/sdd/roadmap.md` | `ROADMAP.md` |
   | `.docs/sdd/changelog.md` | `CHANGELOG.md` |
   | `.docs/sdd/constitution.md`, `architecture.md`, `estimation.md`, `estimation-log.md` | `.docs/sdd/steering/<doc>` |

   Fix them in the live documents (`CLAUDE.md`, `AGENTS.md`, `README.md`, `capabilities/`, `steering/` and those at the root). The ADRs of `decisions/` aren't touched, because they're immutable: the report lists their broken links. `CHANGELOG.md` is history: only its links are fixed, by item 5 and by this step. The mentions of skill names are step 5's.

5. **Skill names.** If this search returns something (a path that doesn't exist, like a project without `AGENTS.md` or without `.claude/`, doesn't count):

   ```bash
   git grep --untracked -nE 'sdd-(start-feature|start-patch|end-feature|end-patch|consult|init-greenfield|init-brownfield)' -- CLAUDE.md AGENTS.md ':(glob).docs/sdd/*.md' ':(glob).docs/sdd/steering/*.md' ':(glob).docs/sdd/capabilities/*.md' ':!.docs/sdd/changelog.md' ':!.docs/sdd/client-changelog.md' ':!.docs/sdd/roadmap.md' .claude/skills .claude/commands
   ```

   Replace each name, and nothing else:

   | The 2.x | The 3.0.0 |
   | --- | --- |
   | `sdd-start-feature`, `sdd-start-patch` | `sdd-propose` |
   | `/sdd-start-feature`, `/sdd-start-patch`, the command | `/sdd-propose`, with the slash |
   | `sdd-end-feature`, `sdd-end-patch` | `sdd-archive` |
   | `sdd-consult` | `sdd-explore` |
   | `/sdd-consult`, the command | `/sdd-explore`, with the slash |
   | `sdd-init-greenfield`, `sdd-init-brownfield` | `sdd-init` |

   A path `sdd-start-feature/references/…` isn't replaced: it goes to the report. What it finds in `.docs/sdd/capabilities/`, and a line elsewhere that records a dated measurement («on 2026-09-25, 2 of 2 subjects of `sdd-end-patch` stopped…»), goes to a **gate** table instead. The table proposes keeping only the lines where the old name is a datum —one that names the old and the new name, or records a measurement— and replacing it in every other line, a capability scenario included. Elsewhere, no gate: it's a name, and the dev-lead sees it in the diff; the report lists the changed files. The history isn't touched: `specs/`, `changes/`, `releases/`, `kit-feedback/`, `decisions/`, `CHANGELOG.md`, and `changelog.md`, `client-changelog.md` and `roadmap.md` while they stay in `.docs/sdd/`. Without any mention, skip the step and say so.

6. **Estimation method.** If `.docs/sdd/steering/estimation.md` exists. With the two lines of the 2.x template, replace them, no gate. The first 2.x line:

   ```text
   - El `walkthrough.md` registra el tiempo real. Si la desviación supera el ±30 %, …
   ```

   becomes this 3.0.0 line, with the rest of the line the same:

   ```text
   - El `walkthrough.md` registra el tiempo real. Cuenta desde el arranque de la sesión que abre el trabajo, con la investigación previa; una espera a una respuesta del dev-lead va aparte, con su duración. En Claude Code lo mide `sdd session tokens`. Si la desviación supera el ±30 %, …
   ```

   The second 2.x line:

   ```text
   - Los patches registran solo el tiempo real.
   ```

   becomes this 3.0.0 line:

   ```text
   - Los patches estiman en la pregunta de su carril y escriben la estimación y la hora de inicio antes del fix; al cerrar, el tiempo real, contado igual. Una estimación que llega en el commit de cierre se marca `(post hoc)` y el log la deja fuera de la calibración: escrita con el real delante, no estima nada.
   ```

   With another method text (rewritten by the project, or a loose line like «Método: horas por task.»): **gate** — show the project's text next to the two new lines, and apply what the dev-lead approves. «Notas de calibración» is never touched. Without `estimation.md`, skip the step and say so.

7. **Marker.** With the gates of steps 1 to 6 resolved, add to `.gitignore` the line `.temp/` if it's missing, without duplicating it, and create the file if it doesn't exist (if the line was already there, say so); run `sdd upgrade --root "<raíz>" --project-hook`, no gate: it leaves `.claude/hooks/sdd-kit-loaded.mjs` and its entry in `hooks.UserPromptSubmit` of `.claude/settings.json`, so that a session without the kit warns about it; run the «Verification», then `sdd upgrade --root "<raíz>" --mark 3.0.0`, and make the commit `chore(sdd): migrar al kit v3.0.0`. With a gate pending, neither marker nor commit, as `sdd-upgrade` says.

8. **Project rules the kit already covers.** After the commit of step 7, and in its own commit. Read `CLAUDE.md`, `AGENTS.md`, `PRODUCT.md` and `.docs/sdd/steering/*.md`, and look for each work rule that repeats or contradicts the installed kit. **gate** — show a table:

   | Project rule | Where | Kit | Clashes or repeats | Proposal |
   | --- | --- | --- | --- | --- |
   | «el id de una feature se elige a mano» | `steering/constitution.md:7` | `skills/sdd-propose/references/nombrado.md` | clashes | remove it |

   «Kit» is the path, inside the plugin (`${CLAUDE_PLUGIN_ROOT}`), of the file that fixes the rule: open it and check that it fixes it before putting it in; a rule without a path that covers it doesn't go to the table. With the dev-lead present, the table ends with the question «¿Aplico estas propuestas?» and you wait for their answer before the final report: don't take it as pending yourself. The proposal is to remove it, keep it or rewrite it. Apply only the rows the dev-lead approves, in the commit `chore(sdd): reglas del proyecto que ya cubre el kit`. Without the «sí», the table goes to the report as pending, with «para reanudar: pide «revisa las reglas del proyecto contra el kit»»: it doesn't hold back the marker, which is already written. Without any rule to list, skip the step and say so.

9. **Gates `sdd merge --verify` doesn't accept, and gates with lint.** Since 3.0.0, `sdd merge --verify` launches the gate as arguments, without a shell. Read in `.docs/sdd/steering/operations.md` §Testing the line «Gate de merge» and, if there isn't one, «Gate de cierre» (with step 2 pending, the one of `.docs/sdd/tech-stack.md`). No gate, and without touching the line: choosing the task is the project's. The report carries, for each warning, one of these lines as is, with the gate line between « »: the first if it carries `&&`, `||`, `;`, `|`, `>` or `<` outside quotes, the second if it carries `$`, `%…%` or `~`. Also read «Gate de cierre» and, if either of the two lines runs a lint or format task (a task or a script whose name carries `lint`, `format` or `prettier`), the third, without touching the line; a typecheck or build one doesn't warn. Each warning goes as it's written, without adding or removing anything: the lint one doesn't name `sdd merge --verify`.

   ```text
   Gate que encadena comandos: «<línea>» — sdd merge --verify ya no lo admite; hazlo una tarea de moon o un script de package.json
   Gate con variables: «<línea>» — sdd merge --verify no las expande; ponlas en la tarea de moon o en el script
   Gate con lint: «<línea>» — el lint va en «Lint», al editar y en el pre-commit; sácalo del gate
   ```

   With nothing to warn about, skip the step and say so.

10. **Superpowers is no longer needed.** After the commit of step 7, and in its own commit. It runs if `.claude/settings.json` meets one of these two: it has `enabledPlugins["superpowers@superpowers-marketplace"]`, with any value; or it has `extraKnownMarketplaces["superpowers-marketplace"]` and no other `*@superpowers-marketplace` at `true`. If not, skip the step and say so. **gate** — ask, as is:

    ```text
    El kit ya no usa superpowers. ¿Quito su activación de `.claude/settings.json`? Si el proyecto usa sus skills fuera del kit, di que no y se queda como está.
    ```

    With the «sí», remove `enabledPlugins["superpowers@superpowers-marketplace"]`; remove the marketplace too, unless another `*@superpowers-marketplace` is at `true`: then you keep it and say which plugin uses it (one at `false` doesn't use it). Make the commit `chore(sdd): quitar la activación de superpowers`. It doesn't uninstall anything or touch `~/.claude/settings.json`. Without the «sí», don't write anything; it doesn't hold back the marker, which is already written, and the report carries, as is:

    ```text
    Superpowers sigue declarado en `.claude/settings.json`. Para quitarlo más tarde, borra `enabledPlugins["superpowers@superpowers-marketplace"]` y, si ningún otro plugin activado sale de ese marketplace, `extraKnownMarketplaces["superpowers-marketplace"]`.
    ```
