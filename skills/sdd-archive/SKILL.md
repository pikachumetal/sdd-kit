# sdd-archive

## Overview

Closing a change is a **Definition of Done**: a checklist that keeps the project's documents from going stale and closes the improvement loop. **Closing = running the WHOLE checklist**, not noticing the code is there. Write everything the user reads in the language of their message. One trunk for every lane, with short branches marked `Feature only:`, `Patch only:` and `Hotfix only:`; a step without a mark applies to all. The merge step forks `finishing-a-development-branch` of superpowers 7.0.0 (MIT, see `NOTICE`).

**Violating the letter of the checklist is violating its spirit.** Skipping a step «because it's small» or «because there's a rush» is when the documents start to drift.

**Escalation clause** (`Patch only:`): if the `Decisiones` list of `patch.md` §3 has a decision about what the user sees or can do with author `sin el dev-lead`, or the fix ended up interpreting requirements, it was a feature: close it with the `Feature only:` branches and say so.

## Checklist (one todo per step)

0. **Pre-checks** — in this order, before writing any record:
   1. `git status --porcelain` in the worktree. If anything shows, stop and ask: «Hay cambios sin commitear: `<ficheros>`. ¿Los commiteo en la rama, los descarto o paro?». Discard nothing without the answer.
   2. `node "${CLAUDE_PLUGIN_ROOT}/cli/bin/sdd.js" merge --check --project-root "<worktree>"` (`Hotfix only:` `--check --into <stable>`). With `destino sacado:`, stop with its output before writing anything.
   3. `git worktree list`: every other `feature/*` or `patch/*` branch it shows goes in one line of your next message, before any other step of the close and even if you stop for item 1, and you go on: «Abiertas a la vez: `<rama>` (`<ruta>`). La que fusione segunda integra la base y repite sus gates.»
   4. `Patch only:` is `patch.md` complete (§2-§4)? `Feature only:` is the spec approved (`status: approved`, approvals signed)? If not, POINT IT OUT before going on: closing over a draft spec is an anomaly the user accepts explicitly and the walkthrough records. Read `mode:` in its frontmatter (no field = `full`): in `lite` there is no `plan.md` or `tasks.md`; don't ask for them and skip step 2's `tasks.md`.
   5. `Hotfix only:` ask «¿Alguno de estos patches pide algo al proyecto (un fichero, una clave, un paso a mano)?», alone in its turn and in any profile, and wait: only the dev-lead knows what the project must apply, and the diff doesn't tell you. Their answer decides step 7's migration step.
   6. `Feature only:` the final review. Check there was one, and with which axes and models: `sdd-implement` runs it with `sdd-verify`, and the thread records it in the `Revisión final:` line of `tasks.md` (without `tasks.md`, in the axes' report of this session); a 2.x line, without axes, counts too. Compare `HEAD` with the last reviewed commit: the second sha of `Re-revisión:`; if none, the `sobre` of `Revisión final:`; if the line says «juntada en el cierre», the closing commit. If it moved with a commit the thread doesn't review (the exception of «Every commit of yours» in `sdd-implement`: under 20 lines, only documentation or comments): without `Re-revisión:` in `tasks.md`, dispatch the single re-review of `<last reviewed>..HEAD` as «Closing the review» of `sdd-verify` says ([encargo-revision.md](../sdd-verify/references/encargo-revision.md)), with its silence watch, record `Re-revisión: <sha>..<sha>, sdd-kit:effort-high + opus, <verdict>`, and write nothing until it's back and closed; with `Re-revisión:` already there, don't dispatch another: the walkthrough carries `sin revisar: <sha> — <qué cambia>` in ✋. If it didn't move, don't launch another review. Only with no final review at all, invoke `sdd-verify` for it.

   If step 7 of `sdd-start-feature` left drafts uncommitted (`walkthrough.md`, the merged capability, the changelog entry), the close starts from them: it completes them with the verification, the time and what the review changed, without rewriting them.
1. **Validation** — before touching anything, and always before the merge, even if the `merge` block authorizes it: the «Validación» row of the [gate table](../sdd-start-feature/references/control-profiles.md) applies to every lane.
   - **With `validation.mode: field`** in `.docs/sdd/sdd-kit.json` ([field validation](../sdd-start-feature/references/control-profiles.md#validación-en-campo)), in any profile: you don't ask, don't offer to defer and don't give a script, even if the user is away or only said «cierra». You run your smoke —one row per THEN, and the suite as the bullet **The suite** says— and record `Validación en campo: <fecha> · <verificación del agente>` with the evidence you ran and what is `no probado` as is. If the user does say what they tried, the line is `Validado` with their words. «El kit no define ese valor, no voy a suponer» doesn't hold: that section defines it.
   - **Without the key, with `manual` or another value** (which counts as `manual`; say so): has the user **validated the work** —said **what they tried and that it works**, or answered «sí» without detail to a validation question that already asked for it, which is validation too— or **deferred validation** with its three conditions at once (present with the work in front of them, their words that they'll try it later, a trigger with an owner; in `unattended` the trigger is always the release smoke)? A missing or vague trigger: don't ask again; make the nearest use concrete, with whoever defers as owner, and say it in the final message so they can correct it ([deferred validation](../sdd-start-feature/references/control-profiles.md)). «Cierra», «está implementada», «los tests pasan» or a clean review are not validation: they're the order to close. Without either, STOP before touching anything: present what there is (`Patch only:` the smoke of `patch.md` §4; in a visual adjustment, each screenshot's path, which is what the user looks at to validate, and the detector's output or its warning, with a line proposing `§Frontend` if `tech-stack.md` lacks it), the **test script**, composed, rehearsed and offered as [dev-validation.md](references/dev-validation.md) says, and your smoke separately, and ask what they tried, alone in its turn, with these three options, labelled like this even in text: `Validado: lo he probado y funciona` · `Diferir: lo pruebo en <uso más próximo, concreto>, a cargo de <quien valida>` · `No funciona`. Choosing «Diferir» without text is the phrase and the trigger: don't ask again. «No funciona» goes back to the fix, and the close starts over. With the user away in `pair` or `delegate`, the close doesn't start: the change waits.
   - **The suite**, in both modes. If step 7 of `sdd-start-feature` already ran it (the validation names its sha; the closing commit moves `HEAD`, not that), don't run it again, whatever the base did: step 6 repeats only what the base brought (`tests/affected-gate-red.md`, g5). If it hasn't run, with another branch open (item 3 of step 0) or the base ahead (`git rev-list --count HEAD..<remote>/<merge.into>` > 0 after `git fetch`), step 6 runs it once (g6); otherwise run the closing gate here. A branch that only touches `.docs/` or `*.md` runs nothing. Otherwise, before the gate, run whole each suite of «Suites» (`operations.md` §Testing, or `tech-stack.md`) with level `unitario`, `pendiente` or none, unless its command is the gate's or one of the tasks the gate runs. If the branch touches a file of «Sin filtro» —without the field, the list of «Running a gate» of `sdd-verify`: manifests, lockfiles, `.moon/**` and build and runner configs (`package.json`, `pnpm-lock.yaml`, `*.csproj`, `tsconfig*.json`, `vitest.config.*`…)—, run the gate without `--affected`, every task of the line with `(sin filtro: cambia el build)`, also the ones the filter would have run. The line names every command that ran before the arrow, the unit suites first: `` Gate: `<suite unitaria>` · `<gate>` → <suite>: corrió <N>/<M> · <tarea>: corrió <N>/<M> (sin filtro: cambia el build) ``. After a red, «Running a gate» of `sdd-verify`. Every run saves its whole output to a file in the session's scratchpad before any `tail`, `grep` or `Select-String` (a red is read from that file: step 6), as [e2e-suite.md](references/e2e-suite.md) says if `operations.md` declares the E2E fields.
   - The record, in the walkthrough (`Patch only:` under the table of `patch.md` §4): `Validado: <fecha> · «<frase literal>»` (with `· no detalló qué probó` for a bare «sí»), `Validación diferida: <fecha> · «<frase literal>» · disparador: <…>`, or `Validación en campo: …`. A «Validado por el dev-lead» the dev-lead didn't give is an invention, not a record.
2. **Event record**:
   - `Feature only:` **`walkthrough.md`**, traced from `walkthrough-template.md` of `sdd-templates`. In the verification, tell **verified by you** (with evidence) from **reported by the user**. «4.1 Builds» gives the `Gate:` line of the validation's run, its duration, configuration (the gate's, or what you added) and sha, or «sobre el commit de cierre» if step 5 squashes that sha, and then `--verified-at` carries the closing commit's; a run of step 6 goes in the final message, because the walkthrough is in the closing commit. «Decisiones tomadas sin el dev-lead» gets the execution's rulings: from `## Rulings` of `tasks.md` and, if the workspace still exists, `node "${CLAUDE_PLUGIN_ROOT}/cli/bin/sdd.js" ledger rulings <plan>`; they add up. Then **`tasks.md`** (`full` with more than one task): every row with its final status and commit; fix and note any mismatch with reality.
   - `Patch only:` **`patch.md` finished**: the real commit hash —the fix's—, the verification with the real smoke (verified by you apart from reported by the user) and the time spent. Never blank.
   - **Real time** *(if `.docs/sdd/estimation.md` exists)*: never blank. A deviation beyond ±30 % needs its cause; if you don't know the time, ask, and without an answer approximate it and say so. Run `node "${CLAUDE_PLUGIN_ROOT}/cli/bin/sdd.js" session tokens --path <worktree> --branch <rama>` and paste its lines unchanged (in a patch, `Esfuerzo real` in §5). `Esfuerzo real` counts from the start of the session that opened the work, without waits; outside Claude Code the lines say «no medido».
3. **Living docs**:
   - `Feature only:` **learnings**: each learning of the walkthrough goes where it lives, by type: [aprendizajes-skills.md](references/aprendizajes-skills.md). If the destination doesn't exist, create it from its template in `sdd-templates`, put the learning there and say «`<documento>` no existía: creado desde la plantilla» in the final report; never leave it only in the walkthrough or move it to another document. Without a template for it, don't invent one: say it and add a debt row. A workaround you write into `tech-stack.md` (or `operations.md`) —a setting that dodges a defect instead of fixing it— gets its own debt row too, with a link to the line: a workaround recorded as a decision never reaches the debt.
   - `Feature only:` **skills review** — «no aplica» is decided by looking, not by omission: [aprendizajes-skills.md](references/aprendizajes-skills.md).
   - **The old literal of a `MODIFIED`**: before merging, search the old clause of each `MODIFIED` (its `(antes: …)`, or each phrase of the living requirement it changes) in the whole capability file. Each appearance outside that requirement is fixed through the artifact's delta —a `MODIFIED` of the other requirement, or the «Reglas de la capacidad» entry with its full value—, never by hand, and the walkthrough or `patch.md` names it.
   - **The capability delta** merges with `node "${CLAUDE_PLUGIN_ROOT}/cli/bin/sdd.js" capability merge --path .docs/sdd --artifact <spec.md | patch.md>`, never by hand: copying the block carries `- Se valida en:`, `- motivo:` and `(antes: …)` into the living capability. If it fails it writes nothing: fix in the artifact what its message says and run it again. `Patch only:` compare the capability that describes the piece the fix touched with what it does now, as [records.md](references/records.md#capabilities-of-a-patch) says: no delta when the fix brings it back, never a new capability. Then, before the closing commit, `node "${CLAUDE_PLUGIN_ROOT}/cli/bin/sdd.js" capability check --path .docs/sdd --artifact <artifact>` ([merge recipe](references/merge-recipe.md)): a failure in what you merged or in the artifact's «Capacidades» block you fix; never the validator.
   - **ADR**: `Feature only:` for each «ADR candidata» of the spec, write `decisions/NNNN-<slug>.md` from `adr-template.md`, numbered after the highest, and record this line, literal, in the walkthrough: `ADR: <candidata> → decisions/NNNN-<slug>.md`. Then `node "${CLAUDE_PLUGIN_ROOT}/cli/bin/sdd.js" decision check --path .docs/sdd`, with or without candidates, in a patch too: go on only on exit 0. ADRs don't split failures: an ADR you didn't write stops the close too; fix it or ask.
4. **Indexes**:
   - **Changelog** *(if `.docs/sdd/changelog.md` exists)*: an entry through `add-to-changelog`. `Patch only:` `Fixed` for a failure; `Changed` for a presentation-only adjustment (§2 with the intent), not `Fixed`; `Added` or `Changed` for a closed request, as it adds or changes what the user can do; `Removed` for a removal.
   - **Roadmap** (with `ROADMAP.md` at the root, the 3.0.0 form of [records.md](references/records.md#roadmap-300): the row stays in Now, and debt closes in `debt.md`): the change's own row only changes its «Estado» cell, with no prefix: `✅` needs the validation recorded; deferred, `🧪 validación diferida a <disparador>` instead, until the dev-lead says what they tried; in field, `✅`. A debt or backlog row the change settles —another row, never its own— starts with `**[<Feature|Patch> <id>, <AAAA-MM-DD>: saldada — <enlace>]**`, or `parcial — <enlace>; queda: <lo pendiente>]**`, linking the walkthrough or `patch.md`; the original text stays intact behind it, and no «✅» in its cell. Discovered debt → a debt row. `Patch only:` a row in the «Patches» table (date, id, description): a patch without a row is invisible; deferred, its «Patches» row starts with `🧪 validación diferida a <disparador> — `. A «Patch:» row of «Próximo» for this patch is marked `✅` and stays; it isn't removed. Then the rest of [records.md](references/records.md): the release table of a deferred patch, a re-measured row, and `sdd roadmap check` before the closing commit.
   - **estimation-log** *(if `.docs/sdd/estimation.md` exists)*: `node "${CLAUDE_PLUGIN_ROOT}/cli/bin/sdd.js" estimation log --root "<raíz>"` regenerates it whole from the walkthroughs and patches: no rows by hand, no copy in the project (`.tools/sdd/` or `tools/sdd/` are old copies: say so). If it warns your walkthrough doesn't read, fix the time block, not the script; only if the kit's CLI isn't available, add the row by hand and say so.
5. **History** — `Patch only:` the patch stays in two commits from the `merge-base`, the fix (code, tests, `patch.md`) and the close (`patch.md` with the fix's hash and the time, plus changelog, roadmap, debt, estimation-log and merged capabilities); a fix in several commits is squashed first and `patch.md` gets the squashed hash. `Feature only:` squash the close into one commit from the last task's, with the fixes of the final review and the validation ([commit-milestones.md](../sdd-start-feature/references/commit-milestones.md)). Before squashing, rewrite in `tasks.md` each `Pasada de fix:`, `Re-revisión:` or `Revisión final:` line whose sha falls in the squashed range, without the sha: `Pasada de fix: juntada en el cierre, <n> hallazgos RED→GREEN`. The same with any sha of the range that `walkthrough.md`, `patch.md`, the debt or an ADR of the branch cites (a cited sha is any 7 to 40 hex characters): rewritten without it, or that range isn't squashed. After the closing commit, `git merge-base --is-ancestor <sha> HEAD` holds for every cited sha.
6. **Integrated base** — after the closing commit: a merge inside the squashed range breaks the history. `sdd merge --sync --project-root "<worktree>"` integrates `<remote>/<merge.into>` as the branch's last commit and resolves what the recipe says. Then, by the case:
   - **`base: conflicto en <files>`** (or `merge: conflicto en`): if every file is a `.md` of `.docs/` outside `capabilities/`, or `ROADMAP.md` or `CHANGELOG.md`, and each hunk joins both sides without dropping text from either and without contradicting itself —a phrase the base adds to a line the branch rewrites, a closing prefix on a row whose «Destino» the base changed—, resolve it, in any profile: keep both, commit the merge through the hook, and name it in the commit body and the final message with this line, as written: `Conflicto de la base resuelto por el agente: <fichero> — <qué juntó de cada lado>`. If one hunk sets the same value two ways (two «Destino», two versions), one side's phrase says the opposite of the other's, or any file falls outside, resolve nothing: a person does, and the close stays «No terminado».
   - **No suite yet** (step 1): the closing gate runs once here, on the sync merge (on `HEAD` if `--sync` said `base: al día`), as «Running a gate» of `sdd-verify` says, and it is the validation's suite. What only the base touched passed the close that brought it: no run without the filter for it, unless it is a file of «Sin filtro».
   - **With a suite**: nothing runs if the base only brought `.docs/` or `*.md`. Otherwise the unit suites run whole, as in step 1. If the base brought a file of «Sin filtro», the gate runs whole, without the filter, and every task of the line carries `(sin filtro: cambia el build)`; if not, the gate runs only where it crosses the branch: with `--affected --base <ref>`, the tasks selected by both `--base <merge.into>` (the branch) and `--base <sha of the validation's suite>` (the base); a task only the base touched doesn't run. A gate that doesn't filter runs whole (E2E: [e2e-suite.md](references/e2e-suite.md)).
   - Record each run with the `Gate:` line of `sdd-verify`, one entry per task, `<tarea>: saltada (<porqué>)` too (`tests/affected-gate-red.md`, g5). The merge carries `--verified-at` with the sha of that run, or of the validation's suite if nothing ran.

   A red suite —here or in step 1— is contrasted by hand: first the failing file alone, with the project's runner, on the branch and at once in a detached worktree of the base prepared as Step 2 of `sdd-worktrees`, without cleaning state or caches; the red task whole, without `--affected`, only if the file passes in both and its error isn't a timeout or a machine resource. Search it in the project's debt before you investigate it; nothing merges before the contrast ends. Green in both, with that error or after the whole task, is «No se repite»: open a debt row of flaky tests with the test, its error line copied whole from the saved output, without «…», and both green passes, and go on with the close, in any profile. If it fails without the branch too, stop with the red report and ask whether to merge anyway, in any profile: merging over a red is the dev-lead's call, not yours ([merge recipe](references/merge-recipe.md)).
7. **Merge** — *(if `.docs/sdd/environments.md` exists)* `env:clean` **BEFORE** the merge. Apply the merge policy of the profile and the `merge` block of `.docs/sdd/sdd-kit.json` ([control-profiles.md](../sdd-start-feature/references/control-profiles.md)): with the block complete and profile `delegate` or `unattended`, merge into `merge.into` without asking, with `--no-ff` if `merge.noFf` is `true`; with the block missing or incomplete, or in `pair`, present it and wait. **The merge is `node "${CLAUDE_PLUGIN_ROOT}/cli/bin/sdd.js" merge`, following the [merge recipe](references/merge-recipe.md)**: never `git merge`, `git pull`, `git push` or `HEAD:<destino>` by hand. If the environment denies it, don't retry: [recipe](references/merge-recipe.md#denied-by-the-environment). Never into `main`, never a tag, except `Hotfix only:`. Any other push and any PR are always confirmed. With `merge.removeWorktree: true`, remove a linked, clean worktree from outside it (`git worktree remove <ruta>`); if git refuses, show the files and ask, never `--force`.

   `Hotfix only:` a `hotfix/*` branch merges into the stable branch only with words of the dev-lead that ask for it (Art. IV), used literally: `sdd merge --branch <branch> --into <stable> --tag <version> --order "<their words>"`, after `git fetch`, and `--push` only if those words ask to publish too; `merge.push` isn't enough. With a yes to the pre-check's question, if the repo has `skills/sdd-upgrade/references/migrations/` (the kit's), write the step in `v<version>.md` there before tagging; in another project, the final message lists it as pending for the dev-lead. On `vuelta: conflicto en`, the script has undone everything: «No terminado», and a person ports the fix and runs the hotfix again ([merge recipe](references/merge-recipe.md#hotfix)).
8. **Kit ticket** — offer the kit's improvement ticket with `sdd-feedback` in this same session, unless this change already has its own, even if the session made another's: clearing the context loses what was learned about the kit. The offer goes in the final message. It isn't a gate: without an answer the close ends and leaves nothing pending.
9. **Final message** — the last message. What the close has to say gathers here, even if it was born earlier. In this order, only what has content:
   1. If you made the deferral trigger concrete: «disparador: <…>, a cargo de <…>; lo elegí yo porque tu frase no lo nombraba, corrígelo si no es el tuyo».
   2. The decisions taken without the dev-lead: open `walkthrough.md` (`Patch only:` the `sin el dev-lead` lines of the `Decisiones` list of `patch.md` §3) and name each in one line, even if another session wrote it; don't summarize. With `field`, a 🦆 before, and the rulings under «✋ Me salí del plan en…».
   3. Each instruction the dev-lead gave before the close and how it ended.
   4. What's pending, with the evidence of a denied or failed merge or push; and, if step 6 ran the gate, its `Gate:` line and its sha; and, if step 6 resolved a conflict, its line `Conflicto de la base resuelto por el agente: <fichero> — <qué juntó de cada lado>`, as written.
   5. What's next, with `parent:` or `proposal:` in the artifact ([records.md](references/records.md#whats-next-in-the-family)), with these lines, literal: «Para acabar la `<madre>` falta: `<id>` — `<título de la fila>`[, …]. Recomiendo `<id>`, la primera del roadmap sin dependencias abiertas.» and its launch prompt; all blocked, instead of the recommendation, «Ninguna se puede arrancar todavía: `<id>` espera a `<ids>`.»; none open and the mother open, «La `<madre>` ya no tiene piezas abiertas: su fila se puede cerrar.» Don't mark the mother's row.
   6. The ticket offer, if step 8 makes it.
   7. The done line, always last. With the branch merged into `merge.into` and the worktree without uncommitted changes: `**Terminado.** <rama> fusionada en <destino> (<hash>) · push: <hecho a <remoto>/<destino> | no hecho: <motivo>> · puedes borrar el worktree <ruta>`. Otherwise: `**No terminado.** Falta <qué>. No borres todavía el worktree <ruta>.` A failed or unauthorized push goes in «push: no hecho» and doesn't change the line; «No terminado» is only for a missing merge or uncommitted changes. Only a linked worktree is offered for removal: if the branch is in the repo's main checkout (`git rev-parse --git-dir` and `--git-common-dir` give the same path), the line ends at the push.

   If the dev-lead later accepts the ticket, writing it repeats the done line: the ticket is a new file of the worktree, pending until committed and merged.

## Red flags — STOP, you haven't closed

- You're about to write a record with uncommitted changes in the worktree, or without `sdd merge --check`.
- `Feature only:` you're about to merge without `walkthrough.md`, or the spec is still `draft` and you haven't pointed it out.
- The real time is blank, or the estimation-log lacks this change's row (with the estimation module on).
- `Feature only:` you haven't opened `.claude/skills/`: the skills review isn't done from memory.
- You haven't touched the roadmap.
- You wrote into `tech-stack.md`, `architecture.md` or `environments.md` a value that already lives in `capabilities/` (a time, a limit, a quota).
- A structural learning stays in the walkthrough, or in `tech-stack.md`, because the project has no `architecture.md`.
- You wrote a workaround into `tech-stack.md` without its debt row.
- You're about to merge without the `Validado:`, `Validación diferida:` or `Validación en campo:` line, without the user deciding it or the `merge` block declaring it, or into `main`.
- `Patch only:` `patch.md` without the fix's commit hash.
- You're about to discard work: list what would be deleted and wait for the typed word `discard`.

| Excuse | Reality |
| --- | --- |
| "Without `architecture.md` there's no living doc for it" / "It shows in the code, no doc needed" | A missing destination is created from its template and said; the code doesn't tell the next feature where new things go. |
| "The user asked me to close: that's validating" | Asking to close is an order, not a test: validating is saying what they tried and that it works. Without it the change waits, except with `validation.mode: field`; «lo pruebo mañana» with an owned trigger is a deferred validation (🧪). |
| "It's a lite feature, the close goes light too" | Lite cheapens planning, not verification. Smoke, walkthrough with real time, changelog and roadmap still apply. |
| "The user is in a rush: minimal walkthrough and done" | The whole checklist fits in minutes. What's skipped today is tomorrow's document drift. |
| "The learning is already in the walkthrough" | The walkthrough is a dead record for the next tasks; the living docs are constitution, architecture and tech-stack. |
| "This project has no skills, I skip that step" | You look at `.claude/skills/`, you don't assume. Maybe this feature creates the first. |
| "The plan says to document the times in tech-stack" | The anchor says where the constant is and links the capability; the value lives only in `capabilities/`. Two copies diverge at the first `MODIFIED`. |
| "The time is in the walkthrough, that's enough" | Without a row in the log there's no calibration factor. |
| "It's trivial and urgent: I merge and go" | Urgency is the first cause of broken merges. Merge only if the user decided it or the `merge` block declares it. |
| "The `merge` block and `delegate` let me merge without asking" | They authorize the merge, not the validation: in `delegate` validation stops, except with `validation.mode: field`. |
| "The roadmap will get updated" | The row costs 30 seconds now; later nobody remembers. |
| "It's all in the patch.md" | `patch.md` documents; the changelog and the roadmap index. Without them the patch is invisible. |
| "Tests passed earlier this session" | Run the suite on the tree you are about to integrate. A green run only proves the tree it ran on. |
| "They obviously want it merged" | Integration is the merge policy's or the dev-lead's decision, never a guess. |
| "They seem done with this — I'll offer to discard it" | Discard happens only when the dev-lead asks for it, in those words. |
| "'Yeah, get rid of it' counts as confirmation" | Only the typed word `discard` authorizes deletion. |
| "The PR is up, so the worktree is clutter now" | PR feedback gets fixed in that worktree. It stays until the work lands. |
