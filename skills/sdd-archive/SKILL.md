# sdd-archive

## Overview

Closing a change is a **Definition of Done**: a checklist that keeps the project's documents from going stale and closes the improvement loop. **Closing = running the WHOLE checklist**, not noticing the code is there. Write everything the user reads in the language of their message. One trunk for every lane, with short branches marked `Feature only:`, `Patch only:` and `Hotfix only:`; a step without a mark applies to all. The branch step brings the text of `finishing-a-development-branch` of superpowers 7.0.0 (MIT, see `NOTICE`) where the kit works the same way, and changes it where the kit decides otherwise.

**Violating the letter of the checklist is violating its spirit.** Skipping a step «because this one is small» or «because there's a rush» is exactly when the documents start to drift.

**Escalation clause** (`Patch only:`): if the `Decisiones` list of `patch.md` §3 has a decision about what the user sees or can do with author `sin el dev-lead`, or the fix ended up interpreting requirements, it was a feature: close it with the `Feature only:` branches and say so.

## Checklist (one todo per step)

0. **Pre-checks** — in this order, before writing any record:
   1. `git status --porcelain` in the worktree. If anything shows, stop and ask: «Hay cambios sin commitear: `<ficheros>`. ¿Los commiteo en la rama, los descarto o paro?». Discard nothing without the answer.
   2. `node "${CLAUDE_PLUGIN_ROOT}/cli/bin/sdd.js" merge --check --project-root "<worktree>"`. With `destino sacado:`, stop with its output before writing anything: a close written for a merge that can't happen is rework.
   3. `git worktree list`: every other `feature/*` or `patch/*` branch it shows goes in one line of your next message, before any other step of the close and even if you stop for item 1, and you go on: «Abiertas a la vez: `<rama>` (`<ruta>`). La que fusione segunda integra la base y repite sus gates.»
   4. `Feature only:` is the spec approved (`status: approved`, approvals signed)? If not, POINT IT OUT before going on: closing over a draft spec is an anomaly the user accepts explicitly and the walkthrough records. Read `mode:` in its frontmatter (no field = `full`): in `lite` there is no `plan.md` or `tasks.md`; don't ask for them and skip step 2's `tasks.md`. Lite cheapens planning artifacts, never verification.
   5. `Hotfix only:` ask «¿Alguno de estos patches pide algo al proyecto (un fichero, una clave, un paso a mano)?», alone in its turn and in any profile, and wait: only the dev-lead knows what the project must apply, and the diff doesn't tell you. Their answer decides step 7's migration step.
   6. `Feature only:` the final review. Check there was one, and with which axes and models: `sdd-implement` runs it with `sdd-verify`, and the thread records it in the `Revisión final:` line of `tasks.md` (without `tasks.md`, in the axes' report of this session); a 2.x line, without axes, counts too. Compare `HEAD` with the last reviewed commit: the second sha of `Re-revisión:`; if none, the `sobre` of `Revisión final:`; if the line says «juntada en el cierre», the closing commit. If it moved with a commit not reviewed in the thread —the thread reviews a commit under 20 lines (`git diff --numstat`) that only changes documentation or comments: files under `.docs/`, `*.md` of any path that aren't an agent's instructions or a template, comment lines no tool interprets; in a merge, only what the thread resolved, with `git show --remerge-diff`—: without `Re-revisión:` in `tasks.md`, dispatch the single re-review of `<last reviewed>..HEAD` as «Closing the review» of `sdd-verify` says ([encargo-revision.md](../sdd-verify/references/encargo-revision.md)), with its silence watch, record `Re-revisión: <sha>..<sha>, sdd-kit:effort-high + opus, <verdict>`, and write nothing until it's back and closed; with `Re-revisión:` already there, don't dispatch another: the walkthrough carries `sin revisar: <sha> — <qué cambia>` in ✋. If it didn't move, don't launch another review. Only with no final review at all, invoke `sdd-verify` for it.

   If step 7 of `sdd-start-feature` left drafts uncommitted (`walkthrough.md`, the merged capability, the changelog entry), the close starts from them: it completes them with the verification, the time and what the review changed, without rewriting them.
1. **Validation** — before touching anything, and always before the merge, even if the `merge` block authorizes it: the «Validación» row of the [gate table](../sdd-start-feature/references/control-profiles.md) applies to every lane.
   - **With `validation.mode: field`** in `.docs/sdd/sdd-kit.json` ([field validation](../sdd-start-feature/references/control-profiles.md#validación-en-campo)), in any profile: you don't ask, don't offer to defer and don't give a script, even if the user is away or only said «cierra». You run your smoke —one row per THEN, and the full suite— and record `Validación en campo: <fecha> · <verificación del agente>` with the evidence you ran (`suite 3/3 · smoke 2/2 THEN con ejecución real · revisión final Spec y Código sobre 7dab58e, re-revisión limpia`) and what is `no probado` as is. If the user does say what they tried, the line is `Validado` with their words. «El kit no define ese valor, no voy a suponer» doesn't hold: that section defines it.
   - **Without the key, with `manual` or another value** (which counts as `manual`; say so): has the user **validated the work** —said **what they tried and that it works**, or answered «sí» without detail to a validation question that already asked for it, which is validation too— or **deferred validation** with its three conditions at once (present with the work in front of them, their words that they'll try it later, a trigger with an owner; in `unattended` the trigger is always the release smoke)? A missing or vague trigger: don't ask again; make the nearest use concrete, with whoever defers as owner, and say it in the final message so they can correct it ([deferred validation](../sdd-start-feature/references/control-profiles.md)). «Cierra», «está implementada», «los tests pasan» or a clean review are not validation: they're the order to close. Without either, STOP before touching anything: present what there is (`Patch only:` the smoke of `patch.md` §4; in a visual adjustment, each screenshot's path, which is what the user looks at to validate, and the detector's output or its warning, with a line proposing `§Frontend` if `tech-stack.md` lacks it), the **test script** (numbered steps, each an action in the app and its expected result) and your smoke separately, and ask what they tried, alone in its turn, with these three options, labelled like this even in text: `Validado: lo he probado y funciona` · `Diferir: lo pruebo en <uso más próximo, concreto>, a cargo de <quien valida>` · `No funciona`. Choosing «Diferir» without text is the phrase and the trigger: don't ask again. «No funciona» goes back to the fix, and the close starts over. With the user away in `pair` or `delegate`, the close doesn't start: the change waits.
   - The record, in the walkthrough (`Patch only:` under the table of `patch.md` §4): `Validado: <fecha> · «<frase literal>»` (with `· no detalló qué probó` for a bare «sí»), `Validación diferida: <fecha> · «<frase literal>» · disparador: <…>`, or `Validación en campo: …`. A «Validado por el dev-lead» the dev-lead didn't give is an invention, not a record.
2. **Event record**:
   - `Feature only:` **`walkthrough.md`**, traced from `walkthrough-template.md` of `sdd-templates`. In the verification, tell **verified by you** (with evidence) from **reported by the user**. «4.1 Builds» gives the full suite's command, result, duration and the sha it ran on (the integrated base's, if step 6 ran it again). «Decisiones tomadas sin el dev-lead» gets the execution's rulings: from `## Rulings` of `tasks.md` and, if the workspace still exists, `node "${CLAUDE_PLUGIN_ROOT}/cli/bin/sdd.js" ledger rulings <plan>`; they add up. Then **`tasks.md`** (`full` with more than one task): every row with its final status and commit; fix and note any mismatch with reality.
   - `Patch only:` **`patch.md` finished**: the real commit hash —the fix's—, the verification with the real smoke (verified by you apart from reported by the user) and the time spent. Never blank.
   - **Real time** *(if `.docs/sdd/estimation.md` exists)*: never blank; deviation threshold and what to do if you don't know it in [estimation.md](references/estimation.md). Tokens and cost aren't written from memory: run `node "${CLAUDE_PLUGIN_ROOT}/cli/bin/sdd.js" session tokens --path <worktree> --branch <rama>` and paste its lines unchanged (in a patch, `Esfuerzo real` in §5). `Esfuerzo real` counts from the start of the session that opened the work, without waits; outside Claude Code the lines say «no medido».
3. **Living docs**:
   - `Feature only:` **learnings**: each learning of the walkthrough goes where it lives, by type: [aprendizajes-skills.md](references/aprendizajes-skills.md). If the destination doesn't exist (an `architecture.md` postponed at init), create it from its template in `sdd-templates`, put the learning there and say «`<documento>` no existía: creado desde la plantilla» in the final report; never leave it only in the walkthrough or move it to another document. Without a template for it, don't invent one: say it and add a debt row. A workaround you write into `tech-stack.md` (or `operations.md`) —a setting that dodges a defect instead of fixing it— gets its own debt row too, with a link to the line: a workaround recorded as a decision never reaches the debt.
   - `Feature only:` **skills review** — «no aplica» is decided by looking, not by omission: [aprendizajes-skills.md](references/aprendizajes-skills.md).
   - **The capability delta** merges with `node "${CLAUDE_PLUGIN_ROOT}/cli/bin/sdd.js" capability merge --path .docs/sdd --artifact <spec.md | patch.md>`, never by hand: copying the block carries `- Se valida en:`, `- motivo:` and `(antes: …)` into the living capability. If it fails it writes nothing: fix in the artifact what its message says and run it again. `Patch only:` open the capability that describes the piece the fix touched and compare it with what it does now. If the fix only brings it back to what the capability says, there's no delta: «Capacidades» says `Ninguna, porque el fix devuelve <comando> a lo que ya dice <nombre>`, and an empty delta section of the template goes. If it changed something observable the capability says otherwise or doesn't say, the block says `- Modificadas: <nombre> — cambia «<requisito>»` and the delta goes in «Delta de capacidad». A patch creates no capability: with none describing the piece, `Ninguna, porque ninguna capacidad describe <pieza>`, and the final message says so. Then, before the closing commit, `node "${CLAUDE_PLUGIN_ROOT}/cli/bin/sdd.js" capability check --path .docs/sdd --artifact <artifact>` ([merge recipe](references/merge-recipe.md)): a failure in what you merged or in the artifact's «Capacidades» block you fix; never the validator.
4. **Indexes**:
   - **Changelog** *(if `.docs/sdd/changelog.md` exists)*: an entry through `add-to-changelog`. `Patch only:` `Fixed` for a failure; `Changed` for a presentation-only adjustment (§2 with the intent, not a root cause), not `Fixed`; `Added` or `Changed` for a closed request, as it adds or changes what the user can do; `Removed` for a removal.
   - **Roadmap**: the change's own row only changes its «Estado» cell, with no prefix: `✅` needs the validation recorded; deferred, `🧪 validación diferida a <disparador>` instead, until the dev-lead says what they tried; in field, `✅`. A debt or backlog row the change settles —another row, never its own— starts with `**[<Feature|Patch> <id>, <AAAA-MM-DD>: saldada — <enlace>]**`, or `parcial — <enlace>; queda: <lo pendiente>]**`, linking the walkthrough or `patch.md`; the original text stays intact behind it, and no «✅» in its cell. Discovered debt → a debt row. `Patch only:` a row in the «Patches» table (date, id, description): a patch without a row is invisible. A «Patch:» row of «Próximo» for this patch is marked `✅` and stays; it isn't removed. Then the rest of [records.md](references/records.md): the release table of a deferred patch, a re-measured row, and `sdd roadmap check` before the closing commit.
   - **estimation-log** *(if `.docs/sdd/estimation.md` exists)*: `node "${CLAUDE_PLUGIN_ROOT}/cli/bin/sdd.js" estimation log --root "<raíz>"` ([estimation.md](references/estimation.md)).
5. **History** — `Patch only:` the patch stays in two commits from the `merge-base`, the fix (code, tests, `patch.md`) and the close (`patch.md` with the fix's hash and the time, plus changelog, roadmap, debt, estimation-log and merged capabilities); a fix in several commits is squashed first and `patch.md` gets the squashed hash. `Feature only:` squash the close into one commit from the last task's, with the fixes of the final review and the validation ([commit-milestones.md](../sdd-start-feature/references/commit-milestones.md)). Before squashing, rewrite in `tasks.md` each `Pasada de fix:`, `Re-revisión:` or `Revisión final:` line whose sha falls in the squashed range, without the sha: `Pasada de fix: juntada en el cierre, <n> hallazgos RED→GREEN`. A commit can't carry its own hash.
6. **Integrated base** — after the closing commit, not before the records: a merge inside the range you squash would break the history. `git fetch`; if `<remote>/<merge.into>` isn't an ancestor of `HEAD`, `git merge --no-edit <remote>/<merge.into>` in the change's worktree, as the branch's last commit. A conflict only in the three registers you resolve as the recipe says; any other, `git merge --abort` and a person resolves it. The full suite runs again on the result only if the base brought changes outside `.docs/` that aren't `*.md`, and the merge carries `--verified-at <sha of the last green full suite>`: the suite runs once per tree, not once per step. A red suite —here or in step 1— is contrasted by hand without the branch and searched in the project's debt before you investigate it; if it fails without the branch too, stop with the red report and ask whether to merge anyway, in any profile: merging over a red is the dev-lead's call, not yours ([merge recipe](references/merge-recipe.md)).
7. **Merge** — *(if `.docs/sdd/environments.md` exists)* `env:clean` **BEFORE** the merge: removing a worktree with its environment alive leaves orphan containers holding ports. Apply the merge policy of the profile and the `merge` block of `.docs/sdd/sdd-kit.json` ([control-profiles.md](../sdd-start-feature/references/control-profiles.md)): with the block complete and profile `delegate` or `unattended`, merge into `merge.into` without asking, with `--no-ff` if `merge.noFf` is `true`; with the block missing or incomplete, or in `pair`, present it and wait. **The merge is `node "${CLAUDE_PLUGIN_ROOT}/cli/bin/sdd.js" merge`, following the [merge recipe](references/merge-recipe.md)**: never `git merge`, `git pull`, `git push` or `HEAD:<destino>` by hand, except the sync merge of the recipe. If the environment denies the merge, don't retry it: the report quotes the literal command, the denial's text and the destination's hash. Never into `main`, never a tag, except `Hotfix only:`. Any other push and any PR are always confirmed.

   `Hotfix only:` a `hotfix/*` branch merges into the stable branch only with words of the dev-lead that ask for it (Art. IV), used literally: `sdd merge --branch <branch> --into <stable> --tag <version> --order "<their words>"`, after `git fetch`, and `--push` only if those words ask to publish too; `merge.push` isn't enough. Without such words, don't merge into the stable branch. Its pre-check is `sdd merge --check --into <stable>`. With a yes to the pre-check's question, if the repo has `skills/sdd-init-brownfield/references/migrations/` (the kit's), write the step in `v<version>.md` there before tagging; in another project, the final message lists it as pending for the dev-lead. On `vuelta: conflicto en`, the script has undone everything: «No terminado», and a person ports the fix and runs the hotfix again ([merge recipe](references/merge-recipe.md#hotfix)).
8. **Kit ticket** — decide whether you offer the kit's improvement ticket with `sdd-feedback` in this same session: offered unless this change already has its own, even if the session made another's, because clearing the context loses what was learned about the kit. The offer goes in the final message. It isn't a gate: without an answer the close ends and leaves nothing pending.
9. **Final message** — the close's last message. What the close has to say gathers here, even if it was born earlier. In this order, and only what has content:
   1. If you made the deferral trigger concrete: «disparador: <…>, a cargo de <…>; lo elegí yo porque tu frase no lo nombraba, corrígelo si no es el tuyo».
   2. The decisions taken without the dev-lead: open `walkthrough.md` (`Patch only:` the `sin el dev-lead` lines of the `Decisiones` list of `patch.md` §3) and name each in one line, even if another session wrote it; don't summarize. With `field`, a 🦆 before, and the rulings under «✋ Me salí del plan en…».
   3. Each instruction the dev-lead gave before the close and how it ended.
   4. What's pending, with the evidence of a denied or failed merge or push.
   5. The ticket offer, if step 8 makes it.
   6. The done line, always last. With the branch merged into `merge.into` and the worktree without uncommitted changes: `**Terminado.** <rama> fusionada en <destino> (<hash>) · push: <hecho a <remoto>/<destino> | no hecho: <motivo>> · puedes borrar el worktree <ruta>`. Otherwise: `**No terminado.** Falta <qué>. No borres todavía el worktree <ruta>.` A failed or unauthorized push doesn't change the line: the branch is merged and the worktree can go; the reason goes in «push: no hecho». «No terminado» is only for a missing merge or uncommitted changes. Only a linked worktree is offered for removal: if the branch is in the repo's main checkout (`git rev-parse --git-dir` and `--git-common-dir` give the same path), the line ends at the push.

   If the dev-lead later accepts the ticket, writing it repeats the done line: the ticket is a new file of the worktree, pending until committed and merged.

## Red flags — STOP, you haven't closed

- You're about to write a record with uncommitted changes in the worktree, or without `sdd merge --check`.
- `Feature only:` you're about to merge without `walkthrough.md`, or the spec is still `draft` and you haven't pointed it out.
- The real time is blank, or the estimation-log lacks this change's row (with the estimation module on).
- `Feature only:` you haven't opened `.claude/skills/`: the skills review isn't done from memory.
- You haven't touched the roadmap.
- You wrote into `tech-stack.md`, `architecture.md` or `environments.md` a value that already lives in `capabilities/` (a time, a limit, a quota).
- A structural learning stays in the walkthrough, or in `tech-stack.md`, because the project has no `architecture.md`.
- You wrote a workaround into `tech-stack.md` without its debt row.
- You're about to merge without the `Validado:`, `Validación diferida:` or `Validación en campo:` line, or into `main`.
- You're about to discard work without the user's word for it.

| Excuse | Reality |
| --- | --- |
| "Without `architecture.md` there's no living doc for it" / "It shows in the code, no doc needed" | A missing destination is created from its template and said; the code doesn't tell the next feature where new things go. |
| "The user asked me to close: that's validating" | Asking to close is an order, not a test. Validating is saying what they tried and that it works. Without it the checklist doesn't start; with the user away the change waits, except with `validation.mode: field`, which validates in the field. «Lo pruebo mañana», present and with an owned trigger, does close: a deferred validation (🧪). |
| "It's a lite feature, the close goes light too" | Lite cheapens planning, not verification. Smoke, walkthrough with real time, changelog and roadmap still apply. |
| "The user is in a rush: minimal walkthrough and done" | The whole checklist fits in minutes. What's skipped today is tomorrow's document drift. |
| "The learning is already in the walkthrough" | The walkthrough is a dead record for the next tasks; the living docs are constitution, architecture and tech-stack. |
| "This project has no skills, I skip that step" | You look at `.claude/skills/`, you don't assume. Maybe this feature creates the first. |
| "The plan says to document the times in tech-stack" | The anchor says where the constant is and links the capability; the value lives only in `capabilities/`. Two copies diverge at the first `MODIFIED`. |
| "The time is in the walkthrough, that's enough" | Without a row in the log there's no calibration factor. |
| "It's trivial and urgent: I merge and go" | Urgency is the first cause of broken merges. Merge only if the user decided it or the `merge` block declares it. |
| "The `merge` block and `delegate` let me merge without asking" | They authorize the merge, not the validation: in `delegate` validation stops, except with `validation.mode: field`. |
| "The roadmap will get updated" | The row costs 30 seconds now; later nobody remembers. |
| "It's all in the patch.md" | `patch.md` documents; the changelog and the roadmap index. Without them the patch is invisible. |
| "Tests passed earlier this session" | Run the suite on the tree you are about to integrate. A green run only proves the tree it ran on. |
| "They obviously want it merged" | Integration is the merge policy's or the dev-lead's decision, never a guess. |
| "They seem done with this — I'll offer to discard it" | Discard happens only when the dev-lead asks for it, in those words. |
| "This other worktree looks stale — I'll clean it too" | Clean up only this change's worktree. Everything else belongs to someone else. |
| "Removal refused — `--force` is just finishing the cleanup" | The refusal means files exist only in that worktree. `--force` destroys them permanently. Show them and ask. |
