# sdd-propose

## Overview

The single entry for a change: it reads the project, classifies the change into a lane and writes what comes before implementing (spec and plan, or the patch's opening). This project works with **Spec-Driven Development**: the spec is the source of truth, the code is output. Artifacts (folders, names, document structure) follow the kit's convention.
<!-- kit: incluye user-language -->

**Golden rule:** artifacts live ONLY in `.docs/sdd/changes/<task-folder>/`. Never create `docs/superpowers/` or leave loose plans.

**Breaking the letter of the gates is breaking their spirit.**

## ⛔ Gate 1 — On invocation: load context and STOP

Invoking this skill does NOT mean "run the whole SDD now". It is step 0: prime the SDD context. Two paths, depending on how the invocation arrives:

- **Alone** (`/sdd-propose` with no statement, or the skill triggered before the user says what they want): read the SDD context. If the branch is `feature/<id>` and `<id>` has a pending roadmap row, that row is the statement: go on to step 2. Otherwise **STOP** until they state the change. Don't spend a turn asking «which task?» when the branch already says it.
- **With a statement** (`/sdd-propose <change>`, or the change in the same message that triggers the skill): read the SDD context and **continue** to step 2 without stopping to ask what to do — the statement is there.

**Before the statement, DO NOT** explore the feature's code (grep / `semble` / Read of the implementation). The SDD context is the **docs**, not the code — and you don't know the task yet. With the statement, step 2 looks at the code only to classify.

| Rationalization | Reality |
| --- | --- |
| "I need to explore the code to have context" | The SDD context is the docs (constitution, architecture…). Exploring code before the statement is premature and burns tokens on assumptions. |
| "I'll prepare something meanwhile" | There is no "meanwhile". Context → stop. |

## Checklist per change (one todo per step)

**Phase notice** — every time you move to another step, or to a phase inside one (coherence pass, review, integration), your message opens with a plain line: `Ahora: <qué haces, dicho sin número de paso>. Queda: <lo que falta hasta la próxima parada del usuario>, ~<minutos>`, and `, ~<dólares>` if the step launches subagents or subjects. A counter («van 7 de 15») or a step number alone doesn't tell the user where they are.

**The announcement** of a feature or a spike: the notice that leaves step 2, with these lines under it, before the first design question and with no confirmation question; they open the understanding note of step 4:

```text
Carril: feature, modo full · Perfil: delegate, del proyecto (sdd-kit.json)
Aviso: se ignora merge.push de sdd-kit.local.json: solo admite control.profile, execution y validation.startEnvironment; lo demás es del proyecto y va en sdd-kit.json.
Si te vas a ausentar: «apruebo la spec por delegación, nos vemos en la validación» (o «…, y paras antes de la Task 1 para que baje la sesión a gama media», con el modelo más capaz y más de una task)
Para otro perfil: «perfil `<otro>` para esta feature»
```

The profile line says which level it comes from; one `Aviso:` line per local key you ignore, literal from [control-profiles.md](references/control-profiles.md); in `pair` and `delegate`, the two phrases. The variant with the Task 1 stop goes only when the session runs on the most capable model and you foresee more than one task, with how many («prevé 3 tasks») and its reason: in Native the session implements every task and runs well on a mid-tier model (Sonnet, effort medium), lowering only Opus's effort is not mid-tier, and the session can't change its own model: after approval there is no other stop where the user can (Art. IV). With a single task, don't offer it: rebuilding the cache after switching models costs more than a short task saves. If they choose it, approve the spec, write the plan, put the opening in its commit and stop before Task 1 whatever the method, saying the change (`/model`, Sonnet with effort medium) and that they say «sigue» when ready.

1. **Context** — read `PRODUCT.md`, `ROADMAP.md` and `.docs/sdd/steering/` —constitution, operations, architecture— (+ `capabilities/` if it exists — `capabilities/<capability>.md` is the living truth of behavior). Before opening any capability, run `node "${CLAUDE_PLUGIN_ROOT}/cli/bin/sdd.js" capability index --path .docs/sdd` and read only those that, by their purpose, the change will touch: the file name doesn't say where a rule lives.
2. **Classify** — **check first, in a command of its own, whether dependencies are installed (`node_modules`, `.venv`…); if not, Step 2 of `sdd-worktrees` («Project Setup») goes before any command that runs the project's code, tests or gate**, in this step or a later one. Read only the code the request touches, enough to classify (reproduce a reported failure, find the file a setting lives in): designing the solution is step 4. Exits: a request that only changes planning —adding or reordering roadmap rows, preparing a release, or a client change to the definition of an already split proposal— without asking to do anything yet → NOT a change, use `sdd-roadmap`: opening a spec for it rewrites what was planned; a feasibility question whose output is an **answer** in the chat ("can we…?", "try it quickly") → NOT a change, also when the user asks to try it or invoked this skill: `sdd-explore` probes it without artifacts. Everything else is a change, and goes to one of five lanes:
   - **spike** — an investigation that must leave its evidence: a table of measurements, a measured threshold («¿aguanta `libres` 1.000 reservas? quiero la tabla de medidas»). `mode: spike`: the short form of `spec-template.md`, and the plan's tasks carry «Evidencia». No production code: what comes out goes to its own row.
   - **config** — a change that doesn't alter what the product's user sees or can do: dependencies, CI, environment variables, settings, a typo, a rename or a format outside visible text. A typo in a screen label is visible text given literally: patch. With the lane confirmed, first thing: read [references/config-lane.md](references/config-lane.md) and follow it.
   - **patch** — a small change whose **solution is already fixed**: a **deterministic** failure (the root cause fixes it), a **presentation-only adjustment or removal** (the request fixes it) or a **closed request** that says what changes in what the user sees or can do (the ticket or the dev-lead fixes it). Before you classify a change as patch, asked or not, read [references/patch-lane.md](references/patch-lane.md): the tree, the predicates and the estimate. It goes on in `sdd-implement` (folder prefixed `patch-`, never `feature-`), which verifies an adjustment with a screenshot. If you'd have to fix the text, the place or the rule, it's a feature even if small. A patch is what one test reproduces: the lane question names the test that fails today and the fix turns green (in an adjustment or removal, the screenshot of the current state). If it takes two or more tests of new behaviors, it isn't a patch, even with every literal given: offer lite if its predicate holds, feature if not.
   - **lite** — a bounded change that meets the predicate (conditions in [modo-lite.md](references/modo-lite.md)).
   - **feature** — everything else, in full mode. A request with parts of several lanes goes by its heaviest part: say which part rides inside it («the README typo goes inside this feature»), and never split a part off on your own.

   **Lane in the request.** «patch: …», «lite: …» or «config: …» that your investigation confirms skips the question below. If you see a heavier lane, ask, with the heavier one recommended and what you'd have to decide in it. A request that names a heavier lane than the one you see keeps it: you may offer the lighter one in a question, never move down on your own.

   **Ceremony follows the lane.** Read `.docs/sdd/sdd-kit.local.json` even if it doesn't show when listing the folder; the current profile comes from the feature, that file, the release or the project, and you say which level.
   - **feature and spike announce and go on**, with the announcement above.
   - **patch, lite and config ask**, unless the request names a lane «Lane in the request» lets through, alone and before any branch, folder or id: a numbered prose question ending the turn, recommended first, opened by the 🦆 paragraph of `sdd-rubber-duck` in short mode —in config, which nothing changes for the product's user, the 🦆 says what is touched and which tests run before saving it—. The predicate enables the light lane; the user activates it. A patch's question carries its estimate ([patch-lane.md](references/patch-lane.md)). Lite cites its conditions one by one, says the current profile with the option to change it, and offers the announcement's two phrases as options.
   - **Splitting stays a question**, in every lane: count the internal tasks the statement, read with the code it touches, foresees in the plan. With 3 or fewer never propose splitting; with more than 5, always; with 4 or 5, only if they touch different capabilities or surfaces (DB, UI, API) or one carries a migration, and say which. When it applies, the question replaces the announcement: it proposes splitting into features with their own roadmap row —partition and reason— as the recommended option, next to keeping it whole, says the lane and the profile and offers the announcement's phrases as options. With 4 or 5 tasks on the same surface, no migration, say the count and that you don't split it. If they keep it whole, it isn't proposed again; the new features are numbered as [nombrado.md](references/nombrado.md) says.
   - In `unattended` nothing is asked: patch, config and spike go on, lite goes as full.

   **The lane only goes up.** If doing the change brings in what its predicate excludes —a behavior change in config, a visible decision nobody fixed in a patch, a lite condition that falls—, stop, say it and move up: config to patch or feature, patch to feature, lite to full. Never down.
3. **Branch** — `feature/<id>` from `develop` (id per mode, red flags of ids and folders: [nombrado.md](references/nombrado.md)), or the convention the project's constitution sets. **In `sequence` without a roadmap row: the branch with the script's id is created BEFORE the folder** — it is the act of reserving. **In `sequence`, before the folder, run `node "${CLAUDE_PLUGIN_ROOT}/cli/bin/sdd.js" id claim --project-root "<root>"`**: a reserved id is provisional until its task starts, and the claim checks it against the remote integration and publishes it. If it prints `la <id> pasa a <nuevo>`, it already renamed the branch: the folder and everything after use the new id, and you repeat that line to the user.
4. **Spec** — **First thing in this step: read [references/spec-writing.md](references/spec-writing.md)**: how the spec is written, the design by sections with 4 or more tasks foreseen in full (in `delegate`, to the ✋), what it carries when it applies (a new capability, `§Frontend`, `Se valida en:`), and what happens if the user asks to start right away. Before the interview's first question, invoke `sdd-grilling` with `Skill`: every question follows it. In a feature or a spike, your first message after classifying is the understanding note («what I understood, correct me»), opened by the announcement. Before the sections or `spec.md`, the approaches go in a message of their own that asks which; in `delegate`, in `unattended`, with the spec approved by delegation or after «empieza ya», they go to the spec's Approach. Then create the folder with that same id (naming and predicate modules in [nombrado.md](references/nombrado.md)) + `spec.md` traced from `spec-template.md` of the `sdd-templates` skill, with `mode: full | lite | spike` in the frontmatter.
   **Coherence pass**, in both modes, before dispatching the review and before the gate: first thing, read [references/coherence-pass.md](references/coherence-pass.md) and do it whole —literals, each `MODIFIED` outside the spec, what is retired searched with `git grep` in the whole repo, each real case against its THEN, the delta on a copy—. Then the spec review *(full and lite)*: open [review-spec.md](references/review-spec.md) and apply its rubric: it decides how many reviewers, and the reviewer's brief is there. With the findings folded in, a Crítico accepted or the central decision rewritten sends the second round of its §4 before the gate, also when the review came back before this step. Deciding without opening it is the failure.
   ⛔ **APPROVAL GATE** — per the current profile ([gate table](references/control-profiles.md)): in `pair` and `delegate` present the spec **starting with its 🦆 (from `sdd-rubber-duck` in short mode, also under the title of `spec.md`) and with «✋ Decisiones que he tomado yo — valida estas»** — and WAIT for the user's explicit approval. The gate question, in prose, ends the turn, with fixed numbered options: «Apruebo (Recomendada)» first, «Cambios»; an option that approves or a «sí» counts as approval. A third option, in `delegate` on the most capable model with more than one task foreseen, not the recommended one: «Apruebo; escribe el plan y, si sale Native, para antes de la Task 1 para que baje la sesión a gama media (prevé <n> tasks)», with the announcement's reason. If they choose it, write the plan, put the opening in its commit and, with Native, end the turn saying the change (`/model`, Sonnet with effort medium) and that they say «sigue» when ready; with SDD, go on without stopping. Choosing a scope («just validate X») or answering another question of the turn doesn't approve: the spec stays ON HOLD, even in `delegate`. In `unattended` the agent approves it, with the decisions recorded in that same block, and continues.
   If the user chose or said at the start the phrase that approves the spec by delegation, don't stop either: approve it yourself, record their literal phrase and the date in «Decisiones tomadas con el dev-lead» and in «Aprobaciones», decide the spec review yourself without asking, record it and continue. The rest of the profile's stops stay the same, and so does the validation in step 1 of `sdd-archive`, which `validation.mode: field` does in the field.
5. **Plan** *(full and spike)* — only after the spec is approved. **First thing in this step: read [references/plan-writing.md](references/plan-writing.md)**, then write `plan.md` traced from `plan-template.md` of the `sdd-templates` skill; the method, the header's `Ejecución` line, the closing gate of §3 and where to stop come from that reference and the [gate table](references/control-profiles.md): only `pair` stops at the plan, with the options of the reference, including the Task 1 stop of the announcement. In `delegate` and `unattended`, check that each scenario of the spec has its task, note it in the plan and continue without stopping. Before writing the first task's RED tests, put the opening in a commit (in Native, before its `sdd task start`) ([commit-milestones.md](../sdd-implement/references/commit-milestones.md)).
6. **Hand-off** — implementation lives in `sdd-implement`, and validation and closing in `sdd-archive`: invoke `sdd-implement` with `Skill` once the plan is written (full, spike) or the spec is approved (lite), without implementing anything from here. In `delegate` and `unattended` the plan is not a stop: invoke it in the same turn you write the plan, unless the dev-lead chose to stop before Task 1; it reads `mode` and `profile` from the frontmatter of `spec.md`, the plan's `Ejecución` line and the branch. A confirmed patch goes on in `sdd-implement`, with its class (failure, adjustment or removal, closed request) and the estimate, if there is one. Config ends in its own lane; its `sdd merge` runs as `node "${CLAUDE_PLUGIN_ROOT}/cli/bin/sdd.js" merge`.

## Red flags — STOP and go back to the gate

- You're about to write the spec without having read `references/spec-writing.md` or interviewed with `sdd-grilling`, because "you've already explored the code".
- You're treating the change as small without citing the predicate's conditions, or without the user confirming lite mode.
- You're writing `plan.md` and the spec has no explicit approval from the user.
<!-- kit: incluye unapproved-plan-flag -->
- You're "documenting the decision in the spec" instead of waiting for the answer.
- You're about to ask a full feature to confirm its lane, or to start a patch, a lite or a config change without asking.
- You're about to ask the first design question of a feature or a spike without the announcement.
- In `delegate`, you wrote the plan and are about to end the turn without invoking `sdd-implement`.

| Rationalization | Reality |
| --- | --- |
| "I'd better ask which task it is, so as not to assume anything" | The `feature/<id>` branch with a pending row is already the answer. Spending a turn confirming it separately is the gap: take it as the statement in the announcement or in the lane question. |
| "It's a small, low-ambiguity feature, I have enough context" | That judgment is yours and isn't written anywhere. That's what lite mode is for: cite the predicate's conditions and let the user confirm. |
| "It's one theme, not several loose features; better widen it with the minimum needed" | One theme isn't the criterion: count the internal tasks the plan foresees. With more than 5, or with 4 or 5 touching different surfaces (DB, UI, API) or carrying a migration, the start proposes splitting, not widening the scope. |
| "The reviewers will read it, so the coherence pass can wait" | The pass is yours and goes before dispatching them: a spec approved with a THEN that contradicted its decision cost an amendment and a dev-lead stop. |
| "The user won't answer; I'll continue and document it" | An unapproved spec isn't a contract. The task WAITS at the gate; your last message presents the spec and asks for approval. |
| "In `delegate` the user no longer repeats the gate; from approval on the agent works alone" | Choosing a scope isn't approving. The approval question is explicit and goes alone: without a «sí» or an «apruebo», the spec stays ON HOLD even if the profile is `delegate`. |
| "The request says «patch:», but I'd better confirm the lane" | A lane the request brings and your investigation confirms isn't asked again. Ask only when you see a heavier one. |
