Here is how an export travels, using the March export as the example.

The coworking has five reservations in its data. Three are confirmed in March, one is cancelled in March, and one is in April.

1. **You ask.** You ask for the March 2026 export from the terminal. The command reads the month you typed, "2026-03", and passes it on.
2. **The reservations are loaded.** The tool opens the stored list of all reservations. It reads all five, whatever the month.
3. **The list is narrowed.** The tool keeps the reservations whose day is in March and drops the cancelled one. The April reservation also goes. Three remain. They are sorted by day, then by time slot:
   - Room Norte, 2 March, 10:00–12:00.
   - Room Sur, 5 March, 16:00–17:00.
   - Room Norte, 19 March, 12:00–13:30.
4. **The calendar file is built.** Each reservation becomes one calendar event titled "Sala Norte" or "Sala Sur". The times are stored in the coworking's clock, which is two hours ahead of UTC. The tool converts them to UTC. The 2 March event goes from 10:00–12:00 to 08:00–10:00. The three events are wrapped in one calendar file.
5. **The file is saved.** The tool creates an `exports` folder if it doesn't exist. It saves the file there under the month's name. It then prints the file's location on screen.

After the steps, you open Google Calendar or Outlook and import that file. Your three March reservations appear. This happens outside the tool.

One thing in the code is worth checking. The converted times end without the "Z" that marks UTC. Some calendar apps may read them as local time and show events two hours early. I haven't tested an import to confirm it.

**Where to look**
- Command and month reading: `src/cli.js`
- The chain of steps: `src/export/index.js`
- Loading reservations: `src/bookings/repository.js`, data in `data/bookings.json`
- Month filter, cancelled filter and sorting: `src/export/filter.js`
- Events and the UTC conversion: `src/export/ics.js`
- Saving the file: `src/export/writer.js`
