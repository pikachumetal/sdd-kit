La Task 1 (backend) ya está mergeada (commit b66f169): expone `GET /bookings?status=Confirmed|Pending|Cancelled` (parámetro opcional; sin él, todas), y `Booking` en la respuesta lleva `status` como texto.

Estado actual del frontend (ya en el repo):

- `frontend/src/app/bookings/booking-list.component.ts`: usa `httpResource<Booking[]>(() => '/api/bookings')` sin parámetro de estado.
- `frontend/src/app/bookings/booking-list.component.css`: estilos existentes con `var(--text)` y `var(--surface))`.
- `frontend/src/app/bookings/status-select.component.ts` y `.css`: NO existen todavía, hay que crearlos.

Los tests RED ya están commiteados (commit d03bac3) y fijan el contrato exacto:
- `status-select.component.spec.ts`: el componente `StatusSelectComponent` debe renderizar un `<select>` con cuatro `<option>` cuyo texto sea exactamente, en este orden: "Todos", "Confirmada", "Pendiente", "Cancelada". Debe aceptar un input `disabled` (booleano) que deshabilite el `<select>` nativo.
- `booking-list.component.spec.ts`: `BookingListComponent` debe exponer una propiedad pública `status` que sea un signal escribible (el test llama `fixture.componentInstance.status.set('Cancelled')`). Sin estado elegido, la petición es a `/api/bookings` (sin query). Con estado elegido, la petición es a `/api/bookings?status=<valor>` (ej. `/api/bookings?status=Cancelled`).

Decisiones ya tomadas (no las repienses):
- El tipo `BookingStatus` es una unión de literales `'Confirmed' | 'Pending' | 'Cancelled'` (o enum si encaja mejor con el resto del código; el valor en runtime que viaja a la API y al DOM debe ser el literal en inglés).
- `app-status-select` usa `model<BookingStatus | null>(null)` para el valor elegido (así lo dice el plan en "Produce"), y un `input<boolean>` (nombre `disabled`) para el estado deshabilitado, tal como el test lo ejercita con `fixture.componentRef.setInput('disabled', true)`.
- `booking-list` debe pedir `/api/bookings?status=<valor>` solo cuando `status()` tiene valor; si no, `/api/bookings` a secas. `httpResource` es reactivo a signals leídos dentro de su función URL — usa `status()` ahí dentro para que el resource se recompute solo.
- No hace falta que `booking-list.component.ts` renderice `app-status-select` en su template para que estos dos tests pasen (el segundo test de booking-list solo ejercita el signal `status` directamente), pero la spec de la feature (Delta de comportamiento, "La lista se filtra con un selector") sí pide que el selector esté integrado en la lista real — así que sí, integra `<app-status-select>` en el template de `booking-list`, enlazado al signal `status` vía `[(value)]` (o el nombre que le des al `model`), y pásale `disabled` según `bookings.isLoading()`.
- Estilos de `status-select.component.css`: usa `var(--text)` y `var(--surface)` igual que `booking-list.component.css`, para que el selector se vea coherente en tema claro y oscuro.
