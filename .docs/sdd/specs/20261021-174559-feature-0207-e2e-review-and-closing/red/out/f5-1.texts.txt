### Strengths
- The change is small and does what the commit says: the preference is saved on the server, restored on mount, and covered by an e2e test of the full round trip.
- `Status` is extracted as a type and the component stays a function with hooks, as required.
- The new `/api/prefs/:key` endpoints reuse the structure and style of the existing ones in `api.js`.
- UI text is in Spanish.
- The e2e test waits with `expect.poll` for the server to hold the value before navigating, so it does not depend on the order of the PUT and the navigation.

### Issues

#### Critical (Must Fix)
None.

#### Important (Should Fix)

1. **`server/api.js:112-114`, `src/invoices/InvoiceList.tsx:153,157`: the preference is global, not per user.**
   - `prefs` is keyed only by the preference name. The clipboard right above it is keyed by `x-user`, and that header is the existing convention.
   - The component sends no `x-user` in either call.
   - One user's filter is therefore restored for every other user, and the last writer wins.
   - A person who opens the invoice list would reasonably expect to see their own filter, not someone else's.
   - Fix: key the map by `${user}:${key}` and send `x-user` from the client the way the rest of the app does. Then `savedStatus` in `e2e/helpers.ts:53` needs the header too.

2. **`server/api.js` and `src/invoices/InvoiceList.tsx`: whole-file diffs from a line-ending change.**
   - `api.js` was CRLF and is now LF, which `file` confirms on both revisions.
   - With `--ignore-cr-at-eol` the real change is 4 lines in `api.js` and about 14 in `InvoiceList.tsx`, but the diff shows 40 and 52.
   - Besides the noise, it hides the real change from review and from `git blame`.
   - Fix: restore CRLF in both files (or normalise the repo in its own commit).

3. **`src/invoices/InvoiceList.tsx:152-154`: no error handling, no validation, and a race on load.**
   - The GET has no `.catch`. If the server is down or returns a 404 with an empty body, `r.json()` rejects and the promise goes unhandled.
   - `saved.value` is trusted without checking it against `STATUSES`. A stale or invalid value puts the `<select>` on an option that does not exist, and `shown` is then empty.
   - If the user changes the filter before the GET returns, the late response overwrites their choice.
   - The PUT in `choose` (line 157) also has no `.catch`.
   - Fix: check that the value is in `STATUSES` before calling `setStatus`, add `.catch`, and ignore the response if the user has already chosen (a flag, or an `AbortController` in the cleanup).

4. **`playwright.config.ts:7-8`: timeouts raised without a stated reason.**
   - The test timeout goes to 90 s and the `expect` timeout to 20 s, for every spec in the project.
   - This looks like it hides slowness or flakiness, and it makes real failures take longer to appear.
   - It is not tied to the feature.
   - Fix: revert it. If a specific test needs more time, set it on that test.

#### Minor (Nice to Have)

1. **`e2e/0024-remember-filter.spec.ts:24-31`: server state is not reset.**
   - The first test leaves `cobrada` saved on the server. With `workers: 3`, other specs that open `/facturas` can inherit it.
   - Reset the preference in a `beforeEach` or `afterEach`.

2. **`e2e/0024-remember-filter.spec.ts:33-36`: the "cuatro opciones" test.**
   - It checks existing behaviour, not the new feature, and it hard-codes a count.
   - Its name also does not describe a behaviour.
   - Remove it, or rename it to say what it protects.

3. **`src/invoices/InvoiceList.tsx:153,157`: the URL `/api/prefs/invoice-status` is repeated.**
   - It appears twice here and a third time in the helper. Two occurrences are tolerable; name a constant if a third appears in the component.
