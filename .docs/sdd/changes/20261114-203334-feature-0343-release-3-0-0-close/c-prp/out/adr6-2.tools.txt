# Spec — Las reservas sobreviven a cerrar la terminal

🦆 Hoy, si cancelas la reserva de Norte del lunes, cierras la terminal y la abres otra vez, la reserva vuelve a estar ahí: `salas libres 10:00-12:00` dice `Sur` en lugar de `Norte, Sur`. Con este cambio, `salas` guarda el estado en un fichero JSON de tu carpeta personal (`~/.salas/reservas.json`) cada vez que una orden cambia algo, y lo lee al arrancar; así lo cancelado sigue cancelado. ## Intent

Hoy el estado vive en memoria (ADR 0004) y cerrar la terminal lo borra todo: lo cancelado o anulado resucita. Importa porque la herramienta se usa a diario y repetir cancelaciones no es aceptable. Anti-objetivos: perder o pisar reservas por un fichero estropeado; anunciar un cambio que no quedó guardado; que probar toque el fichero real de quien lo usa.

## Approach

- Fichero JSON con la API síncrona de `node:fs` — sin dependencias (arquitectura), legible a mano, y el ADR 0004 ya lo nombraba como alternativa. Coste: sin consultas ni bloqueo.
- SQLite (`node:sqlite`) — consultas y transacciones, pero es experimental en Node 22 (avisos por stderr) y `package.json` declara `>=20`, donde no existe. Coste alto para dos salas.
- Registro de eventos (fichero de solo añadir líneas) — robusto ante cortes sin renombrado, pero hay que reproducirlo al arrancar y no se puede editar a mano: complejidad sin demanda.
- Elegido: fichero JSON — es lo más simple que cumple el objetivo y encaja con «sin dependencias».

Cómo: al cargar `src/app.js` se lee la ruta (`SALAS_ARCHIVO` o `~/.salas/reservas.json`); si no existe, estado inicial de hoy; si existe y es legible, ese estado. Cada función que cambia una reserva con éxito guarda (crea la carpeta si falta, escribe un temporal y renombra) antes de devolver su mensaje.
