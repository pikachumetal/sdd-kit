- The component is still a function with hooks, and the UI text is in Spanish, as the constraints require.

### Issues

#### Critical (Must Fix)
None.

#### Important (Should Fix)
1. **`playwright.config.ts:8-9`: timeouts raised above the declared value.** The brief declares timeouts "por defecto", but the config now sets `timeout: 90_000` and `expect: { timeout: 20_000 }`. The diff has no matching change to `operations.md`. Since the review package leaves out the spec folder, `operations.md` may hold the reason. If it does, the declared timeouts should say so. If it doesn't, remove both lines. They also apply to every test in the suite and can hide slowness.
2. **`e2e/0024-remember-filter.spec.ts:24-35`: neither new test names a core flow.** The core flows are sum a column, export to PDF, and mark an invoice as paid. Remembering the filter is not one of them. The test that counts the four `<option>` elements (lines 33-36) is a rendering detail that a component test would cover better. Move both checks down a layer, to a component test for the option count and the persistence logic.
3. **`e2e/0024-remember-filter.spec.ts:27`: wait on internal state between two user actions.** `expect.poll(() => savedStatus(request))` waits on the API between selecting the filter and navigating, and no comment gives a reason. If the PUT hasn't landed, the test should fail at the final assertion, because that failure is what the test exists to catch. Remove the poll.
4. **`server/api.js:94-96` and `e2e/helpers.ts:53-56`: preferences are global, not per user.** The clipboard and cells endpoints read the `x-user` header, but `prefs` is keyed only by name. One user's invoice filter therefore becomes every other user's filter. A reasonable person would expect the filter to be personal. Key `prefs` by `${user}:${name}`, and have the helper and the component send `x-user` the way the other helpers do.
5. **`src/invoices/InvoiceList.tsx:114-116`: race and no validation on load.**
   - The GET result overwrites the state whenever it arrives, even after the user has already picked a status. A slow response then reverts the user's choice.
   - `saved.value` is not checked against `STATUSES`, so a stale or invalid stored value gets into state and the filter shows no invoices.
   - There is no `.catch`. A failed fetch gives an unhandled rejection, and the PUT in `choose` has none either.
   
   Guard with a cancelled or user-chose flag, check `STATUSES.includes(saved.value)`, and handle errors.

#### Minor (Nice to Have)
- `src/invoices/InvoiceList.tsx:115`: the list first shows "todas" and then jumps to the saved status. That is a visible flash, and a loading state would avoid it.
- `server/api.js:95`: the PUT stores `(await read(req)).value` without validating it. This is possible shallow validation in the style of Ousterhout's "interfaces simpler than implementations" row, so treat it as a judgement call.

### Recommendations
Fix the per-user scoping first, then drop the E2E wait and the timeout overrides. Move the persistence coverage down a layer. If you want a persistence test, add one at the API or component level.
