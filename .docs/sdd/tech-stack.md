# Tech Stack — sdd-kit

- **Contenido**: Markdown (SKILL.md con frontmatter YAML según la spec de agentskills.io + plantillas + evidencia de tests) más **un script PowerShell** — `Build-EstimationLog.ps1`, distribuido con `sdd-templates` (T7, 2026-09-09) — **con tests Pester** en `tests/*.Tests.ps1` sobre fixtures versionadas en `tests/fixtures/`. Comando: `pwsh -NoProfile -Command "Invoke-Pester -Path tests"` (Pester ≥ 5; validado con 6.1.0 en pwsh 7.6). Sin build. La "CI" es local (T8, 2026-09-09): `tests/Skills.Tests.ps1` valida la anatomía de las 11 skills contra el propio repo (`name` igual a la carpeta y kebab, `description` que empieza por «Usar», H1, Overview, enlaces relativos que resuelven, `references/` sin huérfanos, sin `@`, lista de `superpowers:*` igual a la del README, índice de `sdd-templates` igual a `templates/`, manifests) y `tests/Manifests.Tests.ps1` ejecuta `claude plugin validate` (`--strict` sobre `skills/` y `marketplace.json`; sin strict sobre `plugin.json`, cuyo aviso por el `CLAUDE.md` de la raíz es inherente; se salta si no hay `claude` en PATH). El hook `.githooks/pre-commit` bloquea el commit si la suite falla: se activa una vez por clon con `git config core.hooksPath .githooks`. El fichero de pipeline se escribe cuando se decida el hosting (GitHub / Azure DevOps).
- **Distribución dual**:
  - Plugin de Claude Code: `.claude-plugin/plugin.json` (manifest, versión SemVer) + `.claude-plugin/marketplace.json` (source: `.`). Instalación: `/plugin marketplace add <ruta-o-repo>` + `/plugin install sdd-kit@sdd-kit`. Las skills quedan namespaced `sdd-kit:<skill>`.
  - CLI de agent skills: `npx skills add <org>/sdd-kit [-a claude-code] [--skill <nombre>]` — escanea `skills/<nombre>/SKILL.md` e instala la carpeta completa (auxiliares incluidos).
- **Dependencias**: declaradas en el [README](../../README.md#dependencias), que es la fuente única — `superpowers` (obligatoria, resuelta por `plugin.json` contra el marketplace `claude-plugins-official`) y `grilling` (opcional, `npx skills add`). Aquí no se repite la lista: dos copias divergen, y de hecho lo hicieron — este documento listaba 6 skills invocadas y el README 4 (aprendizaje de la task dependencias-declaradas, 2026-09-02).
- **Tests**: para el código ejecutable, Pester con fixtures versionadas (arriba). Para las skills, subagentes (Sonnet) sobre fixtures desechables ("Acme Orders", "TimeTrack") en el scratchpad de sesión. Sin framework: la evidencia es narrativa verificada en disco (`tests/*.md`). Orquestación de los runs con workflows multi-agente: rutas absolutas incrustadas en el script (los `args` llegan serializados), fixtures con git local propio, una copia de fixture por run, y verificación en disco además del autoinforme del agente; operaciones git de subagentes con `cd` explícito (su cwd de PowerShell no persiste). El **molde de la fixture NO lleva `.git`**: el `git init` + ramas + worktree se crean EN la copia por run — un molde con git ya inicializado rompe el `git init`/`worktree add` del setup ("already exists") y contamina el baseline (aprendizaje de la task carril-rama-worktree, 2026-07-22). El prompt/schema del baseline RED debe ser **neutro**: telegrafiar la conducta correcta (p. ej. pedir «qué leíste antes de responder») contamina el baseline y oculta el fallo — la conducta se infiere del log de acciones y se verifica en disco. Un baseline que **no falla** es evidencia válida de que la guidance sobra (Art. I): puede recortar el alcance de la task, no es un contratiempo — y un baseline limpio **en lo que buscabas** puede destapar un fallo mejor: en la task modo-lite el fallo previsto no apareció, pero sí otro que justificaba la misma solución con más fundamento. La **entrega de la skill al subagente va por prompt**, pegando el `SKILL.md` del working tree: el plugin instalado resuelve a una copia en cache (`installPath` de la versión publicada), así que un run que dependa del harness prueba la versión vieja. El **staging por renombrado no prueba una degradación**: sustituir el nombre de una skill por uno inexistente la hace *ininvocable*, no *ausente* — el agente conserva la skill real en su lista y puede caer en ella, como hizo 1 de 2 baselines en la task dependencias-declaradas (2026-09-02). Sirve para comprobar que un error de invocación no descarrila al agente; no sirve para probar qué hace sin la capacidad. Montar un entorno sin una skill concreta es una limitación abierta del método. **Preguntar al subagente *a posteriori*** —tras cerrar el escenario, sin posibilidad de contaminar la conducta ya ejecutada— es método válido para lo que el autoinforme no cuenta: así se supo que 2/2 agentes habían omitido `brainstorming`, dato sin el cual el RED se habría cerrado con la conclusión contraria (aprendizajes de la task modo-lite, 2026-09-02). **Las skills de superpowers NO se pegan**: las resuelve el harness (plugin instalado), y así el RED prueba la integración real entre la versión instalada de superpowers y la versión del working tree del kit (task alineacion-superpowers, 2026-09-07). **El subagente puede invocar con `Skill` la copia en cache de la misma skill que se le pega por prompt** (2/3 GREEN invocaron `sdd-kit:sdd-consult` v0.5.0) y aun así seguir el texto pegado: la entrega por prompt gobierna, pero se anota en la evidencia cuando ocurre. **Cada criterio de éxito de la spec necesita su escenario**: al redactar el RED se detectó que el criterio 2 no tenía ninguno, se añadió E5 a mitad de campaña y fue el único de su skill que falló.
**A/B de no-regresión** (método de los recortes, Art. I ampliado el 2026-09-07): un recorte no se mide contra un baseline vacío sino contra la versión vigente. Control = `SKILL.md` actual, tratamiento = versión recortada más sus `references/`, mismos escenarios (los de su `*-green.md`), y el corte se publica solo si el tratamiento reproduce la conducta del control en TODOS ellos. Evidencia en `tests/<skill>-ab.md`, con los cortes descartados y su motivo — el descarte es el dato caro. Aprendizajes de la campaña de T2 (38 runs, 2026-09-07/08): **(1) una diferencia observada con n=1 por brazo no es un veredicto** — hay que bisecar para atribuirla a un corte concreto y repetir para medir su frecuencia; en `sdd-consult` la primera lectura ("fabricó el patch a mano") resultó falsa, y el fallo real (ejecutar el trabajo entero tras un handoff correcto) apareció 1/5 en tratamiento contra 0/5 en control. **(2) Los `references/` se leen solos**: con el enlace puesto en el punto de uso, 4/4 tratamientos de `sdd-start-task` los abrieron sin que nada se lo ordenara. **(3) El margen depende de la anatomía**: las skills con secciones autónomas admiten −34 %, las de checklist solo −6 % a −14 %, porque su detalle vive dentro de cada paso. **(4) Las fixtures se evaporan**: las de las campañas de julio no sobrevivieron al scratchpad y hubo que reconstruir cuatro con subagentes constructores — que no contaminan, porque no son sujetos del experimento. Presupuestar esa reconstrucción en toda campaña que reutilice escenarios antiguos.
**Entorno sin una skill y sujetos que despachan (T9, spike 2026-09-09)**: las dos limitaciones anteriores se levantan lanzando el sujeto como **sesión headless** en vez de como subagente: `claude -p --settings '{"enabledPlugins":{"sdd-kit@sdd-kit":false}}' --plugin-dir <copia del working tree sin la skill> "<petición>"`. Verificado con sondas desechables: con el kit instalado deshabilitado y una copia sin `sdd-consult`, el sujeto lista las otras 10 skills como `sdd-kit:*`, las 14 de superpowers y `NINGUNA-CONSULT` — la skill está *ausente*, no ininvocable, y se prueba la versión sin publicar sin pegarla por prompt. El mismo sujeto responde `SÍ` a tener herramienta de despacho de subagentes, así que la guidance cuyo efecto es despachar pasa a ser medible con sujetos. Descartados: `--bare` (exige API key sin OAuth; esta cuenta no la tiene) y `claude plugin eval --ablation with-without` (RED/GREEN integrado con brazo sin plugin, pero en early access: se vigila). Coste: una sesión headless con la cuenta compartida por sujeto (~30 s una sonda corta); la fixture se pasa por ruta como hoy. La próxima campaña RED/GREEN lo estrena.
**Los sujetos-subagente no pueden despachar subagentes** (task `workflow-ejecucion`, 2026-09-08): un agente lanzado desde un `Workflow` no tiene herramienta de despacho (`ToolSearch` sin resultados, comprobado por 2/2 sujetos). Toda guidance cuyo efecto sea *despachar* —default de ejecución, modelo y effort del encargo, traspaso de las restricciones al ejecutor aislado— queda fuera del alcance de una campaña con subagentes: lo que sí se mide es que el sujeto *entiende* el default (2/2 lo trataron como delegar y documentaron la desviación en `tasks.md`); el efecto se verifica por **dogfooding** en la siguiente task del kit, con el dev-lead como testigo (Art. VII). Registrado en T9 junto a la limitación del staging por renombrado. **Antes de escribir guidance nueva, buscar si superpowers ya la cubre y dónde**: en T3 dos piezas resultaron estar en superpowers pero fuera del punto de uso (las Restricciones globales en prosa pero no en `task-brief`; el effort solo en `references/codex-tools.md`), y eso es exactamente lo que el Art. IX llama hueco demostrado.
**Un artefacto bien formado es guidance** (tasks `entorno-por-worktree` y `spec-ligera-funcional`, 2026-09-08): tres veces en la release el RED desautorizó guidance de conducta porque el *artefacto* ya la llevaba — el TDD que el Art. II del proyecto empuja (T3), el `environments.md` que el agente lee sin skill (T4), y el delta de la spec ligera que tiene la forma exacta del fichero de capacidad y se fusiona moviendo bloques (T5, E1 3/3). Antes de escribir un paso en una skill, comprobar si la plantilla del input ya obliga a la forma del output: si sí, el paso sobra.
**Aprendizajes de T7** (primer código ejecutable, 2026-09-09): **(1) la revisión final de rama con un modelo superior no es redundante con las revisiones de task** — dos revisiones Sonnet aprobaron un `Substring(0, 8)` sin guardar y una extracción de campos a nivel de documento; la revisión de rama (Opus) las reprodujo con carpetas reales y costó ~25 min de arreglos. **(2) El smoke sobre un repo real es parte del test**: el gate literal de la plantilla (`Tiempo (ligero)`) excluía en silencio un patch de Alybo titulado `## 5. Tiempo`; la tolerancia se decide contra artefactos reales, no contra la plantilla. **(3) Las fixtures acumuladas cruzan umbrales**: tres rondas de arreglos llevaron el conjunto de calibración a n=10 exacto y apagaron el aviso «< 10» que un test daba por hecho — un test de umbral necesita fixtures a ambos lados. **(4) Una restricción de estilo mal formulada produce slop**: «comentarios en castellano» en las Restricciones globales empujó a comentar el *qué*; la regla es el Art. X. **(5) El tool `Agent` no expone effort**: se declara el modelo y el effort queda en el defecto del harness; se anota en `tasks.md` como desviación de forma respecto al Art. IV. **(6) Un reinicio de sesión mata a los subagentes en curso**: se reanudan con `SendMessage` y el ledger de `subagent-driven-development` (`.superpowers/sdd/<plan>/progress.md`) es lo que evita repetir tasks ya hechas.
**Aprendizajes de T8** (2026-09-09): **(1) `claude plugin validate` cubre menos de lo que sugiere el nombre** — detecta frontmatter y `description` ausentes, pero acepta `name: Sdd Consult!` y no mira enlaces ni anatomía; se adopta (Art. IX) y se completa con tests propios. **(2) Los tests estructurales sobre el propio repo son un contrato barato**: al primer pase destaparon dos infracciones reales (Overview ausente en `sdd-templates`, `description` ausente en el marketplace) que tres campañas de A/B no habían visto. **(3) Un GREEN en Windows no prueba el hook**: MSYS sintetiza el bit de ejecución desde el shebang y `claude` siempre está en PATH; el hook commiteado como `100644` y un `Set-ItResult -Skipped` en `BeforeAll` (que convierte el skip en fallo) solo los vio la revisión de código clonando a limpio y filtrando el PATH — la degradación (sin `claude`, sin `pwsh`) forma parte del smoke. **(4) `--strict` se decide por fichero**: el aviso de `plugin.json` por el `CLAUDE.md` de la raíz es inherente al layout del repo, así que ese manifest se valida sin strict y los demás con él.
