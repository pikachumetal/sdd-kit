# Tech Stack — sdd-kit

## Contenido y build

- **Contenido**: Markdown (SKILL.md con frontmatter YAML según la spec de agentskills.io + plantillas + evidencia de tests) más **un script PowerShell** — `Build-EstimationLog.ps1`, distribuido con `sdd-templates` (T7, 2026-09-09) — **con tests Pester** en `tests/*.Tests.ps1` sobre fixtures versionadas en `tests/fixtures/`. Comando: `pwsh -NoProfile -Command "Invoke-Pester -Path tests"` (Pester ≥ 5; validado con 6.1.0 en pwsh 7.6). Sin build.
- **Vigencia de `.docs/workflow/`** (2026-09-20): `tests/WorkflowDocs.Tests.ps1` compara el marcador «Última revisión: kit vX.Y.Z» de los documentos que describen el kit con la versión de `plugin.json`, y comprueba que no nombren artefactos retirados. Son documentación **de este repo** y ninguna skill los lee, así que sin un predicado que falle el desfase vuelve solo: entre julio y septiembre de 2026 siguieron describiendo el carril `hotfix` tres releases después del rename. Subir de versión obliga a releerlos.
- **«CI» local** (T8, 2026-09-09): `tests/Skills.Tests.ps1` valida la anatomía de las 11 skills contra el propio repo (`name` igual a la carpeta y kebab, `description` que empieza por «Usar», H1, Overview, enlaces relativos que resuelven, `references/` sin huérfanos, sin `@`, lista de `superpowers:*` igual a la del README, índice de `sdd-templates` igual a `templates/`, recuento de plantillas del README, manifests) y `tests/Manifests.Tests.ps1` ejecuta `claude plugin validate` (`--strict` sobre `skills/` y `marketplace.json`; sin strict sobre `plugin.json`, cuyo aviso por el `CLAUDE.md` de la raíz es inherente; se salta si no hay `claude` en PATH). El hook `.githooks/pre-commit` bloquea el commit si la suite falla: se activa una vez por clon con `git config core.hooksPath .githooks`. El fichero de pipeline se escribe cuando se decida el hosting (GitHub / Azure DevOps).
- **Git**: git-flow desde el 2026-09-20 — `main` estable, `develop` de integración, `feature/<id>` desde `develop`, el mismo que el kit fija a los proyectos. Remoto público en `pikachumetal/sdd-kit` (antes local-only; ver roadmap). Tags anotados `vX.Y.Z` sobre `main`, en el merge commit del cierre de release. Hook pre-commit versionado en `.githooks/`, que se activa una vez por clon con `git config core.hooksPath .githooks` (T8).

## Distribución

Dual:

- Plugin de Claude Code: `.claude-plugin/plugin.json` (manifest, versión SemVer) + `.claude-plugin/marketplace.json` (source: `.`). Instalación: `/plugin marketplace add <ruta-o-repo>` + `/plugin install sdd-kit@sdd-kit`. Las skills quedan namespaced `sdd-kit:<skill>`.
- CLI de agent skills: `npx skills add <org>/sdd-kit [-a claude-code] [--skill <nombre>]` — escanea `skills/<nombre>/SKILL.md` e instala la carpeta completa (auxiliares incluidos).
- **Hook de sesión** (task 0014): `hooks/hooks.json` declara un `SessionStart` que ejecuta `hooks/session-start` (bash) y, solo con `.docs/sdd/`, inyecta `hooks/router.md`; comportamiento en [`routing`](capabilities/routing.md). Claude Code lo descubre sin tocar `plugin.json`. **Solo llega por el canal plugin de Claude Code**: `npx skills add` no instala hooks y Codex no ejecuta el de Claude Code (superpowers declara `"hooks": {}` en su `.codex-plugin` y allí gana con la `description` de `using-superpowers`); esos canales reciben solo las `description`. Deuda abierta en el roadmap.

**Dependencias**: declaradas en el [README](../../README.md#dependencias), que es la fuente única — `superpowers` (obligatoria, resuelta por `plugin.json` contra el marketplace `claude-plugins-official`) y `grilling` (opcional, `npx skills add`). Aquí no se repite la lista: dos copias divergen, y de hecho lo hicieron — este documento listaba 6 skills invocadas y el README 4 (aprendizaje de la task dependencias-declaradas, 2026-09-02).

## Cómo se testean las skills

Para el código ejecutable, Pester con fixtures versionadas (arriba). Para las skills, **sujetos** (Sonnet) sobre fixtures que se construyen en el scratchpad de sesión, sin framework: la evidencia es narrativa verificada en disco (`tests/*.md`), RED (baseline sin la guidance) → GREEN (con ella), o A/B de no-regresión para los recortes.

**Dentro de un hook de git, `git -C` no basta**: git exporta `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE` y `GIT_COMMON_DIR` a sus hooks, y esas variables ganan a `-C`. Un script o un test que llame a git desde un hook —por ejemplo desde el pre-commit que corre la suite— opera sobre el repositorio del hook, no sobre el que se le pasa: en la task 0001 eso desvió el cálculo de ids y reinicializó el repo de trabajo. Todo código ejecutable del kit que llame a git guarda, vacía y restaura esas cuatro variables (`Get-NextSddId.ps1` es la referencia).

### Fixtures y baselines

- **El molde y lo que produjo cada sujeto se versionan** en la carpeta de la spec (`evidencia-red/`, `evidencia-green/`): el molde, el lanzador, los ficheros que escribió cada sujeto y el `git status` de cada run. Las copias por run y las transcripciones `stream-json` se quedan en el scratchpad. Pesa poco (~150 KB en la task 0002), sobrevive a un apagado a mitad de campaña —pasó en esa task— y deja cada veredicto de `tests/*.md` apuntando a un fichero que se puede abrir. Sustituye a la regla anterior, que declaraba las fixtures desechables.
- **Una fixture que narra una sesión ya pasada deja el árbol en el estado que la bitácora dice**: si la bitácora da por escrito un walkthrough que no existe, un sujeto competente audita la contradicción y su informe parece invención sin serlo. En la task 0002 invalidó el escenario de «sesión limpia» y hubo que repetirlo. Antes de lanzar, contrastar la bitácora con el árbol del molde.
- **Un recorte puede quedarse como forma de la plantilla**: si el baseline escribía sin plantilla y la plantilla introduce la presión (huecos fijos para hallazgos que invitan a rellenarse), el contrapeso va en la propia plantilla —una salida «Sin hallazgos» explícita— y el GREEN comprueba que basta (task 0002).
- **El pre-commit de este repo corre la suite entera y rechaza un test en rojo**: los tests RED del hilo se aparcan fuera de `tests/` (en la carpeta de la spec) y el implementador los mueve con `git mv` en el commit de la implementación. Nunca `--no-verify`. La regla general para proyectos consumidores es alcance de la task 0007.
- **El molde de la fixture NO lleva `.git`**: el `git init` + ramas + worktree se crean EN la copia por run — un molde con git ya inicializado rompe el `git init`/`worktree add` del setup («already exists») y contamina el baseline (task carril-rama-worktree, 2026-07-22). Una copia de fixture por run; verificación en disco además del autoinforme del agente.
- **Un test que crea repositorios nunca cambia el cwd, y no confía en `$TestDrive`**: dentro de una función definida en `BeforeAll`, `$TestDrive` llega `$null`, así que `Join-Path $TestDrive <guid>` da una ruta relativa, `Push-Location` no se mueve y el `git init` + `git add -A` + `commit` del helper caen **en el worktree que ejecuta la suite** (task 0001, 2026-09-20: pasó dos veces y hubo que deshacerlo con `git reset --mixed`). La forma correcta: `git -C <ruta>` siempre, y un directorio temporal propio resuelto y verificado.
- **El prompt del baseline RED debe ser neutro**: telegrafiar la conducta correcta (p. ej. pedir «qué leíste antes de responder») contamina el baseline y oculta el fallo — la conducta se infiere del log de acciones y se verifica en disco. Un artículo de la constitution de la fixture que telegrafía la conducta invalida el baseline igual (T11, E5).
- **Un baseline que no falla es evidencia válida de que la guidance sobra** (Art. I): recorta el alcance de la task, no es un contratiempo — no se fuerza el fallo ni se escribe la guidance igualmente: se reencuadran spec y plan al subconjunto que el baseline sí respalda y **se vuelve a pedir la aprobación** (task carril-rama-worktree, 2026-07-22: de dos comportamientos nuevos quedó un rename y un override). Y un baseline limpio *en lo que buscabas* puede destapar un fallo mejor: en la task modo-lite el fallo previsto no apareció, pero sí otro que justificaba la misma solución con más fundamento (2026-09-02). Nueve recortes en la release 1.0.0.
- **Cada criterio de éxito de la spec necesita su escenario**: en T1 se detectó al redactar el RED que el criterio 2 no tenía ninguno, se añadió E5 a mitad de campaña y fue el único de su skill que falló.
- **Preguntar al sujeto *a posteriori*** —tras cerrar el escenario, sin posibilidad de contaminar la conducta ya ejecutada— es método válido para lo que el autoinforme no cuenta: así se supo que 2/2 agentes habían omitido `brainstorming` (task modo-lite, 2026-09-02).
- **Las fixtures se evaporan**: las de julio no sobrevivieron al scratchpad y hubo que reconstruir cuatro con subagentes constructores (que no contaminan: no son sujetos). Presupuestar la reconstrucción en toda campaña que reutilice escenarios antiguos (T2).
- **Trampas de fixture** (T11, T12): el camino de pregunta de `brainstorming` puede impedir que el sujeto llegue al artefacto medido — la petición cierra las dudas de alcance por adelantado; el código plantado para una review debe ir en un commit propio de la rama, no en el commit base compartido con `main`, o el revisor final señala «la rama no aporta nada».
- **Un stream previo puede ser el RED de otra task** (T16): si una campaña anterior ya es la fixture que pide el §, releer sus `tool_use` con la pregunta nueva vale como baseline a coste cero (los streams de T11 dieron «hilo 0/2, implementador 2/2»).
- **El fixture reproduce la ausencia, no solo el defecto** (task 0011, 2026-09-21): el primer baseline de «nadie marca un nombre real en la spec» salió 2/2 positivo porque la constitution del fixture prohibía los nombres reales; la del kit no lo hace, y ese era el hueco (sin la regla, 0/2). Antes de dar un baseline por limpio, comprobar que el fixture no le da al sujeto una regla que el caso de campo no tenía.
- **El ejemplo de la guidance va en otro dominio que el fixture** (task 0011): una receta de forma con ejemplo del mismo dominio que la campaña le da al sujeto del GREEN la respuesta literal.
- **Un baseline limpio no reproduce los fallos de sesiones largas** (task 0003, 2026-09-21): de catorce conductas que venían de tickets de campo, el kit de develop fallaba en dos. Los fallos de campo salieron con contexto cargado y subagentes; un sujeto recién arrancado con el molde delante hace bien casi todo. Medir el RED **antes** de diseñar la forma de la solución (skill contra referencia, validador), no después: la mitad de la spec aprobada de la 0003 se cayó al leerlo. **Regla**: en una task que edita skills y trae frentes de campo, cada frente se reproduce **antes de presentar la spec** — dos sujetos con el escenario del ticket si es una conducta, verificación leída con fichero y línea si es estructural (una contradicción, un incentivo de la rúbrica). La spec lleva solo los frentes que fallan; los que pasan van a deuda con su evidencia como **posible falso negativo** (ver la entrada de la task 0004 sobre el orden de los mensajes), nunca se descartan sin el dev-lead. El RED/GREEN del delta sigue después de la spec, como siempre.
- **No se implementa en paralelo al RED lo que el RED puede recortar** (task 0003): el validador se despachó mientras corría la campaña «porque no dependía de ella», y dependía, porque su valor era vigilar errores que el RED no mostró. Se revirtió; ~167k tokens de implementador.
- **La evidencia hereda los nombres del fixture** (task 0011): si el fixture planta un nombre real, la evidencia lo anonimiza —citas literales de los sujetos incluidas— antes de commitearse.
- **El orden de los mensajes del caso de campo es parte del fixture** (task 0004): con «cierra la release» seguido de «sí, vX, adelante», 0 de 6 sujetos mostraron la segunda ronda de merge y tag del ticket de campo; con el orden del ticket (la autorización primero y la corrección de versión después), 4 de 4. Un baseline limpio puede ser un guion que no reproduce el caso: releer el ticket y copiar su secuencia antes de declarar que la guidance sobra.
- **El ruido del molde puede tapar la conducta que se mide** (task 0004): un código stub con commits vacíos paró a los sujetos en el gate de entrada antes de llegar al gate de merge. Si pasa, se rehace el escenario sobre un molde sin ruido **en los dos brazos**, no solo en el GREEN; comparar un RED ruidoso con un GREEN limpio no mide la guidance.

### Entrega de la skill al sujeto

- **Con subagentes** (método hasta T9): la skill se pega por prompt desde el working tree; el plugin instalado resuelve a una copia en cache (`installPath` de la versión publicada), así que un run que dependa del harness prueba la versión vieja. **Las skills de superpowers NO se pegan**: las resuelve el harness, y así el RED prueba la integración real entre la versión instalada de superpowers y la del working tree del kit (T1, 2026-09-07). El sujeto puede invocar con `Skill` la copia en cache de la misma skill que se le pega (2/3 GREEN de `sdd-consult` v0.5.0) y aun así seguir el texto pegado: la entrega por prompt gobierna; se anota cuando ocurre.
- **El staging por renombrado no prueba una degradación**: sustituir el nombre de una skill por uno inexistente la hace *ininvocable*, no *ausente* — 1 de 2 baselines cayó a la skill real (task dependencias-declaradas, 2026-09-02). Sirve para comprobar que un error de invocación no descarrila al agente. Resuelto con sesiones headless (abajo).
- **Los sujetos-subagente no pueden despachar subagentes** (T3, 2026-09-08): un agente lanzado desde un `Workflow` no tiene herramienta de despacho (2/2). Con subagentes solo se mide que el sujeto *entiende* el default; el efecto de despachar se mide con sujetos headless. Orquestación de aquellas campañas con workflows multi-agente: rutas absolutas incrustadas en el script — el parámetro `args` del tool `Workflow` puede llegar como **string serializado** y no como objeto: `args.scratchpad` dio `undefined` sin error visible y 3 de 5 runs se perdieron con rutas `undefined\run-*` (2026-07-21); si `args` es imprescindible, validar al inicio (`typeof args === 'string'` → `JSON.parse`) —, y operaciones git con `cd` explícito (el cwd de PowerShell no persiste).

### Sujetos headless (método desde T9, 2026-09-09)

- **Lanzamiento**: `claude -p --model sonnet --settings '{"enabledPlugins":{"sdd-kit@sdd-kit":false}}' --plugin-dir <copia limpia> --add-dir <copia limpia> --permission-mode acceptEdits --allowedTools "Bash(*)" "Agent" --max-turns N --output-format stream-json --verbose "<petición>" < /dev/null`, con cwd en la copia de la fixture. Sin `< /dev/null`, un aviso de stdin precede al JSON. 0,3–2,5 $ y 12–65 turnos por sujeto según lo que haga.
- **La skill está ausente, no ininvocable**: con el plugin instalado deshabilitado y una copia sin la skill, el sujeto lista las demás como `sdd-kit:*` y no ve la retirada; y responde que sí tiene herramienta de despacho, así que la guidance cuyo efecto es despachar es medible (T9). Descartados: `--bare` (exige API key sin OAuth) y `claude plugin eval --ablation with-without` (early access; se vigila).
- **`--plugin-dir` apunta siempre a una copia limpia del kit** (solo `skills/` y `.claude-plugin/`), nunca al working tree: el working tree expone `.docs/` y un sujeto de T10 leyó la spec de la task que lo medía. **`--add-dir <copia limpia>` es obligatorio**: sin él el sujeto no lee `references/` ni ejecuta scripts del plugin (T11). Ojo con `plugin.json` en la copia: durante una release el manifest va por detrás de las migraciones y un sujeto lo usó como versión objetivo (T10).
- **Despachos en primer plano**: un sujeto que despacha con `run_in_background` termina su turno «esperando el informe» y la sesión acaba sin resultado (T14, 0,84 $ perdidos). Con `stream-json --verbose` cada `Agent` expone su `input.prompt`: el traspaso de bloques al encargo (Restricciones globales, Art. X, contrato de tests) es observable (T11, T16).
- **Con dev-lead ausente, la petición cede lo que el sujeto pararía a preguntar** — si no, el sujeto para y no mide, y parar es lo correcto: aprobar de antemano los gates de una migración (T10), «toma tú las decisiones y lístalas» para una spec (T17: 2/2 se pararon en la primera pregunta de brainstorming), «no hubo demo» para un cierre de release (T18: paró en el paso 2).
- **Un gate que aparece después de una respuesta del usuario se mide a dos turnos** (task 0004): primer turno normal, se lee el `session_id` del stream y el segundo mensaje, fijo, va con `claude -p --resume <session_id> "<mensaje>"`, sin simulador. La conducta se lee en el segundo turno y en disco (`git log --all --decorate`). Lanzador de referencia: `red/subject.sh` de la carpeta de la task 0004.
- **Entrevista simulada** (T17): una skill de init se mide con un dev-lead simulado —Haiku con persona fija que responde solo a lo que se le pregunta— y `claude -p --resume` en bucle (`entrevista-driver.py`: 12–16 turnos, 0,4–0,7 $ por sujeto; el agente no detecta al simulador). Se cuenta **lo que el agente pregunta**, no lo que sabe al final: ante una pregunta abierta («¿qué es innegociable?») la persona suelta lo que no se le pidió.

### A/B de no-regresión (recortes, Art. I ampliado el 2026-09-07)

Un recorte no se mide contra un baseline vacío sino contra la versión vigente: control = `SKILL.md` actual, tratamiento = versión recortada más sus `references/`, mismos escenarios (los de su `*-green.md`), y el corte se publica solo si el tratamiento reproduce la conducta del control en TODOS ellos. Evidencia en `tests/<skill>-ab.md`, con los cortes descartados y su motivo — el descarte es el dato caro. De la campaña de T2 (38 runs, 2026-09-07/08):

1. **Una diferencia con n=1 por brazo no es un veredicto**: bisecar para atribuirla a un corte y repetir para medir su frecuencia; en `sdd-consult` la primera lectura («fabricó el patch a mano») resultó falsa, y el fallo real (ejecutar el trabajo entero tras un handoff correcto) apareció 1/5 en tratamiento contra 0/5 en control.
2. **Los `references/` se leen solos**: con el enlace en el punto de uso, 4/4 tratamientos de `sdd-start-task` los abrieron sin que nada se lo ordenara.
3. **El margen depende de la anatomía**: las skills con secciones autónomas admiten −34 %; las de checklist, −6 % a −14 %, porque su detalle vive dentro de cada paso.

## Entorno de trabajo del equipo

- **Sin memoria automática** (2026-09-20): `.claude/settings.json` lleva `"autoMemoryEnabled": false`. La memoria de Claude Code es local a una máquina; lo que se aprende va a estos docs, que viajan en git. Esta sección y varios puntos de «Cómo se testean las skills» salen de migrar las memorias que el agente había acumulado en el PC del dev-lead.
- **Por qué la política de modelos es dura**: el equipo no trabaja contra la API sino con una **suscripción de cuenta compartida** — los tokens que gasta una sesión los pagan también los compañeros. «El modelo más barato que resuelva bien», «`fable` y `opus xhigh` prohibidos por defecto» y «confirmar antes de paralelizar» son una restricción real, no una preferencia. Por eso el modelo se asigna **por task y se documenta en `plan.md`**, donde el dev-lead lo aprueba una vez en lugar de turno a turno: generación mecánica desde un plan detallado y ejecución de escenarios de test → Sonnet; juicio, diseño y verificación adversarial → el modelo del hilo; subir de tier solo en el paso que lo justifique.
- **El repo principal es bare** (desde 2026-09-21, patrón de Orca: repo bare más un worktree por rama). `D:\code\git\sdd-kit` ya no sigue a ninguna rama y no admite commits: todo trabajo, también una edición rápida del roadmap, va en un worktree, con **base corta** (`D:\code\.worktrees\sdd-kit\<nombre>`) porque hay rutas de evidencia de hasta 165 caracteres. Nada —ni un marketplace ni un script— debe apuntar al directorio del repo principal. No se toca `core.bare`: lo gestiona Orca. El plugin se instala desde GitHub (`main`); para probar cambios sin publicar, sujetos headless con `--plugin-dir` sobre una copia limpia del worktree.
- **Trampas de hooks en la máquina del dev-lead**, que cuestan turnos si no se conocen: (1) `block-dangerous-git.js` (en `~/.claude/settings.json`) casa patrones como `clean -f` **dentro del texto inline** de un heredoc y bloquea el comando entero — mover el script a un fichero y ejecutarlo por ruta; (2) el mismo tipo de guarda interpreta `cmd /c "…"` como un `Remove-Item` sobre `/c` (falso positivo, 2026-09-20) — evitar `cmd` y usar PowerShell directo; (3) el hook `*` de Orca (`~/.orca/agent-hooks/claude-hook.cmd`) puede denegar `AskUserQuestion` de forma transitoria — reintentar una vez antes de asumir nada; (4) la guarda de borrado bloquea un comando de PowerShell que escribe un here-string con rutas, aunque no borre nada («Remove-Item on system path '/' is blocked», dos veces en la task 0004 con `Add-Content @'…'@` y un `Replace` en bucle) — escribir con la herramienta de edición; (5) **`bash` del PATH es `C:\Windows\System32\bash.exe`, el lanzador de WSL sin distribución** (exit 127, task 0014): un test que invoque bash por nombre resuelve antes Git Bash (`Resolve-Bash` en `tests/Hook.Tests.ps1`), y un hook no antepone `bash` al comando: delega en `"shell": "bash"`, que Claude Code resuelve a Git Bash.

## Aprendizajes por task (cronológicos)

- **T3 workflow-ejecucion** (2026-09-08): antes de escribir guidance nueva, buscar si superpowers ya la cubre y dónde — dos piezas estaban en superpowers pero fuera del punto de uso (las Restricciones globales en prosa pero no en `task-brief`; el effort solo en `references/codex-tools.md`); eso es lo que el Art. IX llama hueco demostrado.
- **T4 entorno-por-worktree y T5 spec-ligera-funcional** (2026-09-08): **un artefacto bien formado es guidance** — tres veces el RED desautorizó guidance de conducta porque el artefacto ya la llevaba (el TDD que empuja el Art. II del proyecto, el `environments.md` que el agente lee sin skill, el delta de la spec con la forma exacta del fichero de capacidad, E1 3/3). Antes de escribir un paso, comprobar si la plantilla del input ya obliga a la forma del output.
- **T7 Build-EstimationLog** (2026-09-09, primer código ejecutable): (1) la revisión final de rama con un modelo superior no es redundante — dos revisiones Sonnet aprobaron un `Substring(0, 8)` sin guardar y una extracción a nivel de documento; la de rama (Opus) las reprodujo y costó ~25 min. (2) El smoke sobre un repo real es parte del test: el gate literal de la plantilla excluía en silencio un patch de Alybo titulado `## 5. Tiempo`. (3) Las fixtures acumuladas cruzan umbrales: un test de umbral necesita fixtures a ambos lados. (4) Una restricción de estilo mal formulada produce slop («comentarios en castellano» empujó a comentar el *qué*; la regla es el Art. X). (5) El tool `Agent` no expone effort: se anota en `tasks.md` como desviación del Art. IV. (6) Un reinicio de sesión mata a los subagentes en curso: se reanudan con `SendMessage` y el ledger de `subagent-driven-development` evita repetir tasks hechas.
- **T8 skills-validation** (2026-09-09): (1) `claude plugin validate` cubre menos de lo que sugiere el nombre — acepta `name: Sdd Consult!` y no mira enlaces ni anatomía; se adopta y se completa con tests propios. (2) Los tests estructurales sobre el propio repo son un contrato barato: al primer pase destaparon dos infracciones que tres campañas de A/B no habían visto. (3) Un GREEN en Windows no prueba el hook: MSYS sintetiza el bit de ejecución y `claude` siempre está en PATH; la degradación forma parte del smoke. (4) `--strict` se decide por fichero.
- **T10 migracion-consumidores** (2026-09-09): (1) el RED redujo la guidance a una frase de contención — 3/3 baselines siguieron `migrations/README.md` solos y lo único que falló fue hacer *de más*; el riesgo real puede ser el exceso, no la omisión.
